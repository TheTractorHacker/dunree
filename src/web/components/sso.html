Forward auth

Loading...

For every request to a protected site Zoraxy first asks your authorization server. An answer of 200 to 299 lets the request through; any other answer, usually a redirect to the login page, is sent to the visitor.

Sites use Forward auth, but no server is savedThose sites cannot check their visitors until you save the address of an authorization server in step 1.

Point Zoraxy at your authorization server

Works with Authelia, Authentik, OAuth2 Proxy and other servers with a forward auth endpoint. Nothing is checked until an address is saved.

optional

Enter the base URL of your server (for Authentik: of its proxy outpost; no path, no trailing slash) and press its name. This only fills in the fields below; nothing is saved until you press Save changes.

The full address of the endpoint that answers "may this request pass?". Authelia: /api/authz/forward-auth. Authentik: /outpost.goauthentik.io/auth/nginx (or /auth/traefik, /auth/caddy, /auth/envoy).

Authentik outpost options

Only needed for Authentik. Leave everything empty for Authelia and other servers.

Base URL of the Authentik proxy outpost. When set, Zoraxy passes /outpost.goauthentik.io/ (callback, start, sign_out, static files) on every Forward auth protected site to this URL without a login. Authentik needs this so that its session cookie is set on the site's own domain.

Authentik answers 401 with an HTML page to browsers that are not signed in. With a redirect Zoraxy sends browsers to .../outpost.goauthentik.io/start?rd=<original URL> instead. Zoraxy builds the rd value from the request it received; nothing supplied by the client is reflected. API clients still get a plain 401.

    OAuth 2.0

    Loading...

    Zoraxy sends visitors to an identity provider to sign in, checks the answer itself and keeps the session. Your application needs no login of its own; it can read who signed in from request headers.

    1

    Add an identity provider

    Create an application (client) at your provider, then add it here with its client ID and secret. You can add several; each site picks one. A site that picks none uses the provider with the ID default.

    IDNameIssuer / endpointUsed byCallback pathActions
    No identity provider yet. Add one and the sites you choose in step 2 can use single sign-on.

    Callback address to register at the provider

    The provider only sends visitors back to addresses it knows. Register one per protected site:

    Provider "default"
    https://<site>/internal/oauth2
    Any other provider
    https://<site>/internal/oauth2/p/<provider ID>
    Sign out
    <callback address>/logout

    Sessions are stored encrypted in the Zoraxy database and survive a restart. Refresh tokens never leave the server.

    When editing, leave it empty to keep the stored secret. It is never sent back to the browser.

    PKCE (S256) is recommended and works with Authentik. Use PKCE only for providers without S256, and None only for legacy providers.

    Who may sign in, and what your application learns

    Empty fields allow everyone the provider signs in. A site can narrow this further in its own settings.

    Comma separated. A user must be in at least one. A user without the groups claim is refused (403).

    The claim that lists the user's groups. Empty uses groups. Dots reach nested claims (realm_access.roles).

    Exact domain only, subdomains are not included. The e-mail must be verified by the provider.

    Rules look like claim=value1,value2, separated by ;. Every rule must match one of its values, exactly and case sensitively. A missing claim never grants access.

    Examples
    Keycloak realm roles
    realm_access.roles=admin
    Keycloak client roles
    resource_access.my-client.roles=editor
    Microsoft Entra app roles
    roles=Task.Admin
    Microsoft Entra groups
    groups=<guid>
    Authentik groups
    groups=authentik Admins
    Google Workspace domain
    hd=example.com

    Entra leaves the groups claim out for users in more than 200 groups; such a login is refused. The lists of a site are checked in addition to these.

    Header=claim pairs, comma separated. These headers are always removed from incoming requests, so a client cannot fake them, and then set from the verified claims. Host, Authorization, Cookie and forwarding headers cannot be mapped.
