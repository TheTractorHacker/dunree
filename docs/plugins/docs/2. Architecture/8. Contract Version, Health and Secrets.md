# Contract Version, Health and Secrets

Last Update: 23/11/2026

Three optional fields of the introspect let a plugin work better with a Dunree that supervises it. All three are optional, and a Dunree that does not know them ignores them, so a plugin that uses them still runs everywhere.

| Field (JSON) | Go field | What it is for |
|---|---|---|
| `api_version` | `IntroSpect.APIVersion` | which version of the plugin contract your plugin was built for |
| `health_path` | `IntroSpect.HealthPath` | an address Dunree can ask "do you still work?" |
| `configure_via` | `IntroSpect.ConfigureVia` | receive the start configuration (with its secrets) on standard input instead of the command line |

The full contract, with the rules about what may change, is in `docs/plugins/contract.md` of the Dunree repository.

## api_version

The plugin contract is everything Dunree and a plugin say to each other: the introspect, the configure payload, the calls Dunree makes to the plugin and the events. It has a version number. The `dunree_plugin` library of this repository implements contract version `1` (constant `APIVersion`); the library itself has its own version (constant `SDKVersion`, see `CHANGELOG.md` inside the library folder).

**You do not have to do anything.** When you build with `dunree_plugin` 1.1.0 or later, `ServeIntroSpect` adds `"api_version": 1` to your introspect. If you write a plugin in another language, add the field yourself once your plugin follows the contract document.

What Dunree does with it:

- No `api_version` (every plugin built before the field existed): the plugin is a "legacy" plugin. It runs exactly as before and receives exactly the configure payload it always received.
- `api_version` inside the range Dunree supports: Dunree adds two fields to the configure payload, `api_version_min` and `api_version_max`, so the plugin knows what this Dunree understands.
- `api_version` newer than Dunree supports: Dunree starts the plugin anyway and warns the administrator (log, Plugin Manager). The administrator can choose that such plugins are not started at all.

In the plugin you can look at the range:

```go
runtimeCfg, err := plugin.ServeAndRecvSpec(&plugin.IntroSpect{ /* ... */ })
if err != nil {
	panic(err)
}
if !runtimeCfg.ContractSupported() {
	// This Dunree no longer speaks the contract this plugin was built for.
	// RecvConfigureSpec already printed a warning; decide here whether to go on.
}
if runtimeCfg.SupportsAPIVersion(2) {
	// use something that only exists since contract version 2
}
```

`ContractKnown()` is false when Dunree sent no range (an older Dunree). Then only the legacy contract is certain.

## health_path

Without a health address Dunree can only test that the port of your plugin accepts a connection. A plugin that accepts connections but no longer answers (a deadlock, a full queue) looks healthy that way.

Declare a path and serve it:

```go
runtimeCfg, err := plugin.ServeAndRecvSpec(&plugin.IntroSpect{
	// ...
	HealthPath: "/health",
})

http.Handle("/health", plugin.HealthHandler(func() error {
	// return an error while the plugin cannot do its work,
	// for example when a list it needs could not be loaded
	return nil
}))
```

Rules:

- The path is a plain absolute path: letters, digits and `/ - _ . ~`, at most 256 characters, no query string. Anything else is dropped (Dunree then falls back to the port test).
- Dunree sends a `GET`. Any `2xx` status means healthy, everything else and no answer within 2 seconds means not healthy. The request carries the invoke token in `X-Zoraxy-Plugin-Token`.
- Dunree only calls it when the administrator turned the health check of your plugin on (it is off by default), then every 10 seconds. Three failed checks in a row show the plugin as "Unhealthy"; with the option "restart" the plugin is ended and started again.
- Keep the handler fast and do not do real work in it. `plugin.HealthHandler(nil)` is enough when "I can answer" is all there is to say.

## configure_via

By default Dunree starts a plugin with `-configure=<json>`. That JSON holds the API key of the plugin and its invoke token, and a command line can be read by every local user of the machine (`ps`).

Declare `configure_via: "stdin"` and Dunree starts your plugin with the single flag `-configure-stdin` and writes the same JSON document, followed by a newline, to the standard input of the plugin, then closes it:

```go
runtimeCfg, err := plugin.ServeAndRecvSpec(&plugin.IntroSpect{
	// ...
	ConfigureVia: plugin.ConfigureViaStdin,
})
```

`RecvConfigureSpec` (and `ServeAndRecvSpec`) read both ways, so the same binary also runs on a Dunree that does not know the field and still passes `-configure=`.

If you write the plugin in another language: when the first argument is `-configure-stdin`, read standard input to its end (at most 1 MiB) and parse it as the configure JSON.

If your plugin is started through a `start.sh`, the script must hand its standard input and its arguments on to the real program (`exec ./myplugin "$@"`).

The examples `api-call-example` and `filter-example` use both `ConfigureVia` and `HealthPath`.

## API permissions and approval

The endpoints in `permitted_api_endpoints` are shown to the administrator, who can be required to approve them. Two things follow for authors:

- Ask only for what you use, and write a `reason` a person can judge. It is shown next to the endpoint.
- When a new version of your plugin asks for an additional endpoint, an administrator who requires approval has to approve it first. Until then a call to that endpoint is answered as "not permitted" while the rest of your API access keeps working. Handle that answer without failing as a whole.
