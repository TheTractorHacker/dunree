# User-visible changes of the UX redesign

Newest first within each area. Each item names the page and what a user notices; design background is in [audit-2026-11.md](audit-2026-11.md), the components in [components.md](components.md).

## Security Center: CrowdSec (see it in action, more configuration)
* **Security Center > CrowdSec** now leads with what CrowdSec is doing. The header says it in words ("Blocking banned addresses: 1,204 decisions loaded, synced 8 s ago, 37 requests blocked today out of 12,430 checked", or "Watching only: nobody is blocked"), with five counters for today. While it is on, the settings move below the activity.
* **Activity**: a timeline of matched requests (blocked, CAPTCHA shown, would block) for 24 hours or 7 days with all checked requests on a second chart, and top lists of scenarios, sources, countries and sites.
* **Matched requests**: a live list (refreshes every 5 s while you look at it, **Live** pauses it) of each visitor that matched: site, method, path, country, scenario, source, and what Dunree really did. In log-only mode it shows what **would** have been blocked. Filters by outcome, address and text; 25 entries and "Show more".
* **Check an address**: what would happen to an address on a site and why, which loaded decision decides, and optionally what the CrowdSec server itself answers. Click an address in the list to check it.
* **What is loaded** and **Connection health**: decisions by source and type, the pulls and the state changes.
* **New settings** (all optional, nothing changes until you set one): act on, log only or ignore each **source** of decisions (your scenarios, manual bans, community blocklist, subscribed lists); **rules for single sites** chosen from your proxy rules (exempt, log only, enforce; the old typed exempt list shows up here); an **allowlist** of addresses Dunree never blocks; **scenarios kept on log only**; what a captcha decision does on a site **without CAPTCHA**. Two notification events for the CrowdSec server going away and coming back (nothing is sent until you subscribe a channel).
* **Saving** uses the save bar like the other sections (the "Save CrowdSec" button is gone); anything that makes Dunree block more asks first.
* **Fixed**: captcha decisions were counted and listed as "blocked" even when the visitor was served. Counters and the list now show the real outcome.
* **Review fixes**: when the CrowdSec server refuses the key, or no pull has worked yet, the header says so ("The CrowdSec server rejects the API key", "Cannot reach the CrowdSec server yet") instead of "Connecting", the Last sync tile shows the failed attempts instead of a duration, and the error is no longer repeated in the warning box. After a switch-on or restart during the day the three counters read "Blocked since 14:20" instead of "today". The CrowdSec item in the Security Center navigation follows the status of the page (it used to stay "Off" after a change made through the API). Under **Scenarios kept on Log only** each entry shows how many loaded decisions it matches, with a warning when that is half or more.
* Known limits: the counters are not kept across a switch-off, so they can be lower than the "blocked today" badge that reads the persisted log; the reach of a scenario entry is counted on what is loaded right now; matched requests share one lock for their counters (not load-tested under a flood). Counters, lists and history are in memory and start again on a restart (really blocked requests stay in the blocked-request log); the source names are the documented ones and have not been checked against a real CrowdSec. Details: [../guides/crowdsec.md](../guides/crowdsec.md).

## Sites: Error pages (new)
* **Sites > Error pages** (new page): change what a visitor sees when Dunree blocks a request (403), answers 404 or 429, a server is down (521 / 504), the host is unknown or every server is busy (503). ## Database card and offline compaction
* **System > Settings > Database** (new card, admin only, read only): file size on disk, data inside, free space inside, table count, and a table list sorted by size (key count, stored size with a bar, one line on what each known table holds; the first 8 rows, "Show all N tables" for the rest). A large file (200 MB or more) gets a callout saying a Bolt file never shrinks by itself and that offline compaction is available; the "Compact the database file (offline)" help (opened automatically for a large file, otherwise collapsed) shows the exact commands with the real database path: stop the service, `./zoraxy -compact-db -dbpath <path>`, start the service. Nothing is deleted automatically.
* Why this page: Settings is the System page for the instance itself and already a stack of cards; System > Updater and History are about versions and configuration changes, and the card is a one-off look rather than a workflow. Viewers get a 403 from `GET /api/system/dbusage`, and the card hides itself for them. The endpoint reads in one read transaction and stops after 5 seconds ("counting stopped", sizes with a plus sign); it is not part of the `/api/v1` token API.
* `-compact-db` and the growth table of every sys.db table (what grows without a limit, existing caps, recommendations) are in [../db-growth.md](../db-growth.md). Finding: only the `stats` table grows with time and traffic (one record per day, never deleted, per-day caps only).
* **A second Dunree on the same database** no longer hangs silently. Opening BoltDB waits 10 seconds for the lock, then the process exits with status 1 and a message naming the file and the commands `sudo lsof <path>` and `ps -eo pid,etimes,args | grep [z]oraxy` (to the log and to stderr). LevelDB, which fails at once on a lock, gives the same message. Normal start-up is unchanged.

## Certificates
* **Why a manual certificate choice "does not apply" (ERR_ECH_FALLBACK_CERTIFICATE_INVALID)**: the per-host choice is keyed by the host name in the TLS handshake. A browser that offers ECH with a config published by another provider (typically Cloudflare, public name `cloudflare-ech.com`, seen when split DNS sends the host to this proxy while the HTTPS record still comes from Cloudflare) sends only the outer public name, because Dunree cannot decrypt that config. No rule matches that name, so the fallback certificate is served and Chrome rejects it. This cannot be fixed by choosing a certificate: the DNS has to change. Diagnostics only, nothing about which certificate is served changed.
* **Tools > Encrypted Client Hello > Fallback certificate served for these names** (new card, admin only): names that reached the fallback certificate and match no proxy rule or alias (wildcards and aliases are never listed), with a class (ECH outer name of another provider, Dunree's own ECH public name, No SNI, Unknown host / scanner / IP access), count, last seen and a next step. In memory, at most 64 names, since the last restart. API: `GET /api/ech/fallbacks`. The classes of ECH public names live in `src/mod/ech/fallbacks.go` (`KnownECHPublicNames`, `ForeignECHSuffixes`); ordinary unknown names are not guessed at. A foreign ECH name is also logged once per hour per name in plain language.
* **Proxy rule > TLS > Certificate for each hostname**: one info line under the table, shown only when the table above holds an ECH outer name of another provider; it links to the ECH page and takes no space otherwise.
* **ECH > Verify > Check DNS for all hosts**: a foreign ECH config is now called out as the likely cause of ERR_ECH_FALLBACK_CERTIFICATE_INVALID, with the options: override or block the HTTPS (type 65) record in the local resolver, turn ECH off at the DNS provider, publish Dunree's own record for DNS-only hosts, and the quick browser test (chrome://flags/#encrypted-client-hello set to Disabled).
* **New proxy rule > HTTPS certificate** (new field under Domain, no need to open More options): pick which stored certificate the rule serves. Default **Automatic (match by hostname)**: nothing changes and the request is exactly what it was. The list is the same one the TLS tab uses, each entry with its expiry; once a hostname is typed the certificates that cover all of its names (exact or wildcard) are listed first and marked, and choosing one that does not cover a name shows a warning but does not block the rule. The hint under the field lists the names the chosen certificate covers. With no certificates the field says so and links to the Certificates page (the form keeps what was typed). API: `POST /api/proxy/add` (and `POST /api/v1/proxy-rules`) accept `certificate`; an unknown name is refused and nothing is created. The rule and the choice are saved together; the success toast names the certificate and does not offer "Create certificate for this host".
* **Why the choice also turns SNI matching off for that rule**: the server only looks at a rule's preferred certificate when SNI matching is off for that rule (the TLS tab greys the dropdowns out while "Enable SNI" is on). So choosing a certificate in the form stores it for the host and every alias and sets "Enable SNI" off on that rule only; the form says so. Other rules and the default are untouched. A wildcard rule key (`*.example.com`) is now honoured for the names it matches, so a chosen certificate also works for wildcard rules. With SNI matching on and several certificates covering a name, the automatic pick is whichever matches first and is not defined; choosing one removes that ambiguity.
* The Certificates page leads with stat tiles, an **Expiring soon** callout, **Hosts without a certificate** and the certificate list sorted by expiry with status chips; upload / paste / ACME request live in a collapsible **Add a certificate** card. ACME Client is reachable as a tab of the page.

## Overview
* Status gets a **Get started** checklist (first proxy rule, certificate, WAF, backup, notifications); the security score tile stays. Quick Start remains (tour code unchanged) and links to it.

* **Status > Traffic map: Live mode** (new, the default). The map now shows what flows right now, not only today's totals. A strip on top of the map reads **Live: X req/s, Y active** with a pulse dot, and has a **Live | Today** switch (remembered per browser; Today is the old picture of the day's cumulative counters). In Live the edge thickness and the speed of the moving dashes follow the requests per second of the last ~10 s; an edge nothing flows through is grey and does not move at all, so an idle system looks idle. Nodes show `x req/s` and `N active` (requests being served right now, from the load balancer's in-flight counters) or `idle`. The dot stops pulsing and the strip says **Live data unavailable** when an update fails or is older than 6 s, and **Live paused** while the animation is paused or the tab is in the background.
  * Cost: the browser asks `GET /api/stats/livemap` every 2 s, only while the map is on screen, the tab is active and the animation is not paused (**Pause animation** and **Hide** stop all updates). The server derives the rates by diffing the daily counters between two reads, keeps no background goroutine, adds nothing to the request path and answers from a one second cache, so any number of open dashboards cost one sample per second. A counter that goes down (midnight, statistics reset) reads as no traffic. Same login rules as the other `/api/stats/*` reads (viewers may read, not change); not part of the token API.
  * Not available (so not shown): error and blocked rates per rule (only the global `errors/s` and `blocked/s` exist, shown in the strip on wide screens) and TCP/UDP stream proxy connection counts (the stream proxy does not count connections).
  * Prefers-reduced-motion: the dashes do not move (colour, thickness and numbers still tell the story).
* **Status > Traffic map > Tune** (new button in the card header, closed by default, remembered per browser; no new page or menu item): rate analytics to tune rate limits. Choose a window (**10 s, 1 min, 5 min, 1 h**) and see, for all rules and per rule (sorted by peak): **average** req/s, **peak** req/s with the time it happened, the current rate, and, for rules with a rate limit, the **busiest client against the limit** with a plain sentence such as "Your busiest client reached 8 of 10 req/s: a limit of 10 req/s leaves 20% headroom", the number of requests that were rate-limited in the window, and a link that opens that rule's rate limit settings. A **suggested limit** (twice the busiest client's rate) is shown as a hint only; nothing is ever applied automatically. The panel polls every 5 s only while it is open, on screen and the map is not hidden.
  * How it works: ONE background goroutine wakes every 5 s and reads counters that already exist (the per rule daily counters, and the request counters the rate limiter keeps in its per client buckets; the limiter increments two integers while it already holds the bucket lock, nothing else changes on the request path). No persistence: a restart starts with empty history, and the panel says how much of the window is measured so far. A counter that goes down (midnight) reads as no traffic, never as a spike.
  * Memory bound: a 720 slot ring (1 hour of 5 s slots, 5.6 KiB) per rule and one for the total, at most 200 rules tracked (1.1 MiB); a rule with a rate limit adds 23 KiB (denied and busiest client rings); at most 5000 clients are tracked for the busiest client (about 0.5 MiB). Worst case about 7 MiB, typically a few hundred KiB.
  * What is measured per client: only for rules that have the host level **Rate limit** enabled (the limiter is the only place that counts per client; no counter is added for other rules). The busiest client is the one with the most requests in a 5 s slot (shown as req/s and per minute); a client that has not been seen yet in the previous sample has no baseline and is skipped for one tick. Not measured: per client rates of rules without a rate limit (the panel says "Per-client rates are only measured while a rate limit is enabled on the rule"), path rule and ruleset rate limits (only the host level limit is read), and requests of a client whose idle bucket was swept between two samples. Peaks have 5 s resolution: a shorter burst is averaged over its slot. The limit itself is per second with a burst (the unit of the existing setting); per minute figures are the per second figures times 60.
* **Traffic map labels are readable**: node text is larger, and the map is never fitted below 85% zoom. A map that needs less than that is shown from its top-left corner (busiest rules first) with a short "Drag to see the rest of the map" hint instead of 4 px text; the card itself does not change size or overflow.

## Deployment role and forwarded header hardening (dual proxy plan, Phase 2 slice A)
- New setting, Security Center > Deployment: role **Standalone** (default), **External** or **Internal**, plus "Harden forwarded client address headers" (opt-in in Standalone, always on in the other two roles). Stored in sys.db (`settings/deployrole`), so the change history records it ("Deployment role changed"); each change is also written to the system log with the admin name. Old installs have no such key and behave exactly as before: the tests assert a standalone request reaches the router byte for byte unchanged.
- Hardening (`mod/deployrole/headers.go`, applied at the entry of the TLS, plain HTTP, HTTP/3, port 80 and secondary listeners, before health and routing): a peer that is not in the trusted proxy list loses X-Forwarded-For, Forwarded, X-Real-IP, CF-Connecting-IP, CF-Connecting-IPv6, Fastly-Client-IP, True-Client-IP, X-Client-IP, X-Forwarded-Host/Proto/Port and every X-Client-Cert-* header (default site included) and gets a fresh RFC 7239 `Forwarded: for=<peer>;proto=..;host=..`. A trusted peer: client = right-most X-Forwarded-For entry that is not itself trusted (entries to its left are dropped), then CF/Fastly headers, then X-Real-IP, then the peer; X-Real-IP is set to that address so access rules, rate limits, GeoIP and auth exceptions agree; single-address headers that do not parse as one IP, and malformed X-Forwarded-Proto/Port/Host, are removed; `Forwarded` is truncated the same way and this hop appended (a header that does not parse is dropped).
- Auth exception rules with "trust proxy headers" (`UseTrustedProxy`) and the GeoIP locale lookup believe forwarded headers only from a trusted peer while hardening is on.
- Internal role, optional **peer gate** (off until switched on, with a confirm): only trusted proxies and the listed direct-access networks may connect, others get 403 before routing (health endpoint included). The API refuses to enable it when it would refuse every peer (no trusted proxy and no network). Rejections are counted and logged at most every 30 s. Security Overview gets the check "The internal proxy only accepts known peers" (only judged in the Internal role) and the card warns about an internal role without the gate or with an empty trusted proxy list.
- API: `GET /api/deployrole/get`, `POST /api/deployrole/set` (field `config`, JSON), both behind the admin session and CSRF like their siblings.
- Tests: `mod/deployrole` (validation, persistence, gate, full trust matrix, spoofing, multi-hop, IPv6, malformed values), `mod/dynamicproxy/deployrole_hook_test.go` (roles x peers through the real listener wrapper, standalone regression, gate incl. health and port 80, auth exceptions), `dpcore/header_deployrole_test.go` (what the upstream finally sees), `deployroleapi_test.go`, posture check cases.
- Known limits:
  - Not run against a real Cloudflare, UDM or second Dunree: header handling is covered by unit tests only, the two-instance integration test is Phase 5.
  - The existing global/per-rule "Sanitise client IP headers" and "Trust proxy headers only" switches are unchanged and independent; the new hardening does not read them.
  - With hardening on and an empty trusted proxy list, every peer is "direct": forwarded client headers are dropped, so a CDN's visitor addresses are lost until its ranges are listed. The Deployment card warns about it.
  - Hardening trusts what a *trusted* peer sends, as before: an external Dunree in Standalone role that passes a client's CF-Connecting-IP on is outvoted by X-Forwarded-For, but a trusted non-Dunree proxy that does not sanitise is the admin's responsibility. X-Client-Cert-* from a trusted peer are kept (an external proxy may carry verified identity); the per-site client certificate policy still overwrites them where it is set.
  - The upstream request still carries X-Forwarded-Proto set by Dunree itself (existing behaviour); WebSocket upgrades take the same hardened headers because they share the request.
  - The peer gate does not apply to the admin port or the plugin loopback listener. Proxy protocol: the gate and trust decisions use the address after PROXY protocol processing.
  - Not covered by this slice: upstream TLS (CA, pinning), body size limits, SSRF policy, drain on stop.

## Upstream certificate trust: private CA and pinned keys (dual proxy plan, Phase 2 slice B)
- New optional per-upstream settings (Edit site > upstream > Advanced Options > "Upstream certificate trust"): a **CA bundle** (PEM) and **public key pins** (SHA-256 of the SubjectPublicKeyInfo, hex or base64, `sha256//...` accepted). They are used to verify an HTTPS upstream **instead of** "Skip Verification", which stays available and unchanged. Stored in the upstream JSON (`TLSCABundlePEM`, `TLSPinsSHA256`); an old config without the fields behaves exactly as before (tested).
- Rules (`mod/dynamicproxy/upstreamtls`, never weakened): the certificate chain and the host name are always verified; a CA bundle **replaces** the system roots for that upstream only; a pin is **additional** to chain verification (one certificate of the verified chain, the server certificate or its CA, must match one pin; a pin never turns an untrusted certificate into a trusted one); when a bundle or pin is set, Skip Verification is ignored for that upstream (and the legacy TLS 1.0 / weak suite fallback that goes with it is not used); an invalid stored policy fails closed (every handshake refused) and never falls back to skip-verify. Saving refuses a bundle with anything but CERTIFICATE blocks (a pasted private key is rejected, never stored), more than 64 certificates or 256 KiB, a pin that is not 32 bytes, and a policy on an upstream without "Require TLS". Expired CA certificates are accepted on save but shown as expired.
- Used by: proxied HTTP requests (`dpcore.NewDynamicProxyCore`), the **WebSocket** path (which now also honours the rule's SNI / "overwrite host header" name and the upstream client certificate, both were ignored before), the CONNECT / upgrade tunnel (`ProxyHTTPS`, only when a policy is set; without one it behaves as before), the **active health prober** (the policy is part of its config signature, so a change restarts the probes), and the upstream **test tool** (`POST /api/proxy/testupstream` with `cabundle`, `pins`, `ep`; the plain GET form is unchanged). The new-rule dialog now mentions the CA / pin option when a self-signed certificate is detected.
- GUI: textareas for the bundle and the pins, "Check and show fingerprints" (certificate SHA-256 and SPKI pin per certificate, expired flag) and "Test connection with these settings", with helper text recommending CA / pin over skip-verify. API: `POST /api/proxy/upstream/tlsinspect` (`cabundle`, `pins`), the settings travel in the existing upstream add (`cabundle`, `pins`) and update (JSON payload) endpoints, behind the admin session and CSRF like their siblings.
- Posture: new check "Upstream HTTPS certificates are verified" in Security Overview: warns "TLS verification disabled for <rule>" for every rule with an active HTTPS upstream or virtual directory that skips verification and has no CA / pin. Behaviour is not changed, only reported.
- Tests: `upstreamtls` (private CA, unknown CA, wrong host name, expired, not yet valid, pin hex/base64/curl form, pin without chain trust, fail closed, mTLS, bundle parsing incl. private key refusal), `loadbalance/upstream_tls_test.go` (proxied request and health prober must agree on 13 scenarios, mTLS + private CA, config signature, normalisation), `dpcore/upstream_tls_test.go` (HTTP and CONNECT tunnel), `websocketproxy/upstream_tls_test.go` (wss with private CA, pin, SNI override, client certificate, shared dialer untouched), `upstreamtest_tls_test.go` (test tool, handlers, JSON backward compatibility, posture fact), posture check cases.
- Known limits:
  - Virtual directories do not get a CA / pin (only their existing skip-verify flag, which the posture check reports); `HasSameTarget` for bulk virtual directory operations is therefore unchanged.
  - For an upstream addressed by IP and without an "overwrite host header" name, the proxy verifies the certificate against the name of the requested site (existing behaviour of the SNI handling), the health prober and the test tool against the address. Give the certificate both, or set the overwrite host header so all of them use one name.
  - The test tool and the new-rule dialog do not present the upstream client certificate, so an upstream that demands one answers the request with an error even though the certificate check passed. The CA bundle is a full replacement of the system roots, not an addition; to trust both, include the public CAs in the bundle.
  - A pin that is the only setting still needs a chain the system roots trust; for a self-signed upstream put its certificate in the CA bundle (it then serves as its own trust anchor, the host name must still match one of its names).
  - Not tested against real Proxmox, UniFi or other appliances. Nothing here stops a reachable upstream from being a different host: pins narrow that, they are not an authorization of the destination (SSRF policy is a separate slice).

## Request limits, destination guard and admin exposure (dual proxy plan, Phase 2 slice C)
Everything below is off until configured; an existing config or sys.db behaves exactly as before (tests assert it).

- **Per-route limits** (Edit site > Advanced > "Request limits and timeouts"): maximum request body (MiB in the GUI, bytes in the rule JSON `MaxRequestBodyBytes`), request timeout (`RequestTimeout`, seconds) and upstream connect timeout (`UpstreamDialTimeout`, seconds). 0 = off / the built-in 30 s dial. A body whose announced `Content-Length` is over the limit gets `413` before the upstream is contacted; an unannounced (chunked) body is cut by `http.MaxBytesReader` while it is read and also gets `413`. The request timeout covers the whole request (waiting for the upstream); exceeded gives `504`. WebSocket, protocol upgrades and CONNECT are exempt from the request timeout. The limits apply to the TLS path, the plain-HTTP path and virtual directories. API: the existing site edit endpoint takes `maxRequestBodyBytes`, `requestTimeout`, `upstreamDialTimeout`; a parameter that is absent keeps the stored value, a bad value is refused and changes nothing.
- **Global read timeout** (Global settings > Timeouts > "Read Timeout", next to Read Header Timeout): time a client has for the whole request including its body (slow uploads). 0 = off (default, as before). Stored in sys.db (`settings/readTimeout`); `POST /api/proxy/timeouts` takes the new optional field `readTimeout` (older clients that do not send it keep the current value). Applying restarts the proxy, like the other timeouts.
- **Destination guard** (new package `mod/destguard`, the AI assistant SSRF check now uses the same address logic): refuses cloud metadata addresses (169.254.169.254, 169.254.170.2, 100.100.100.200, 192.0.0.192, 168.63.129.16, fd00:ec2::254), link-local, multicast, unspecified and reserved addresses, and the IPv4-mapped, NAT64, 6to4, IPv4-compatible and Teredo forms that carry them. A name is resolved once, every answer is checked (a mixed answer is refused as a whole) and the checked address is the one dialled, so DNS rebinding between check and connect cannot be used.
  - Security Center > **Network exposure** > "Restrict diagnostic tools to allowed destinations" (default OFF) applies it to: the upstream test tool, port scan and IP range scan, uptime monitor checks (including redirects), web terminal target (resolved once and the address handed to ssh) and the HTTP forward proxy. With the switch on, loopback is also refused unless listed, and with an allowed backend list only listed destinations (and ports) are reachable. Metadata and link-local are refused even if listed.
  - **Allowed backend destinations** (CIDR or address, optional ports: `10.20.0.0/24`, `10.20.1.5 443,8000-8100`, `10.0.0.5:443`). When the list is not empty (the switch is not needed for this), a proxy rule upstream, an added or edited upstream, a virtual directory target and the default site target outside it are refused when saved. Empty list = no check = today.
  - The page warns before it bites: it lists the existing rule upstreams that the list or the uptime monitor would refuse.
  - API: `GET /api/destguard/get`, `POST /api/destguard/set` (field `config`, JSON), behind the admin session and CSRF like their siblings; stored in sys.db (`settings/destguard`), recorded by the change history ("Destination restriction changed").
  - The forward proxy has no login (`IsAuthorized` always true). Requiring one would change defaults, so it is only a warning: the "HTTP forward proxy is off" posture check now says it accepts any client without a login.
- **Admin panel allow-list** (Network exposure > "Admin panel allow-list"): CIDRs or addresses that may reach the admin port, enforced as middleware in front of the whole admin listener (UI, API, plugin API, cluster and Fleet endpoints). Empty = no limit (default). Others get `403`. While a list is set, Dunree's own outbound dialers (HTTP, h2c, WebSocket, CONNECT tunnels, virtual directories) refuse to connect to the admin listener's address and port (checked on the resolved address at dial time, so no request header can bypass it and a DNS name is judged by where it really points); a rule pointing at the admin port then fails with a bad gateway instead of reaching the panel from this machine. Lock-out safety: a list that does not contain the saving client's TCP peer address is refused (forwarded headers are ignored for this), and a stored list that no longer validates is ignored. **Recovery**: stop Dunree, start it once with `-reset_admin_allowlist` (clears the list before the admin port serves, logs it), then remove the flag. API: `GET /api/adminallow/get`, `POST /api/adminallow/set`; stored in sys.db (`settings/adminallow`).
- **Posture** (Security Overview): new check "No proxy rule points at the admin interface" (warns (it was a failure in an earlier build of this slice, see the upgrade notes below) and names the rules when an upstream or virtual directory resolves to this instance's admin listener; counted only when it fires, so the score of a clean instance does not change); "Admin port is not open on every interface" fails (instead of warns) when the role is External and the port is on all interfaces without an allow-list, and passes with a note when an allow-list is set; new check "Diagnostic tools only reach approved destinations", judged only in the External and Internal roles.
- Tests: `mod/destguard` (every blocked range incl. mapped, NAT64, 6to4, compat, Teredo; classification; allow-list matching with ports; rebinding simulation: one lookup, checked address dialled; mixed answers; unix and port-less addresses; persistence and corrupt stored value; zero value restricts nothing), `mod/adminallow` (lock-out protection, spoofed headers, dial guard for HTTP / h2c / WebSocket / CONNECT, reset, persistence, corrupt value, rule to admin port detection for wildcard and specific binds), `mod/dynamicproxy/routelimits_test.go` (413 announced and chunked, exact boundary, virtual directory, TLS-path handler, 504, connect timeout, global read timeout with a stalled upload, zero = unlimited), `mod/uptime`, `mod/ipscan`, `mod/forwardproxy`, `mod/sshprox` (guarded dials incl. redirect not followed), posture cases, and in the main package the edit endpoint (partial update, bad limits leave the rule untouched), the timeout API, both new APIs, the upstream test tool under the restriction and rule target validation.
- Known limits:
  - Rule upstream targets are checked when saved (names resolved then). A name that later resolves outside the list is not caught at request time, and existing rules are not changed or removed when a list is set (the page only warns). Per-request dial checking of proxied traffic is not done.
  - With the restriction on, uptime checks of an upstream on loopback or outside the list fail and can take that upstream out of rotation; list those upstreams first (the page shows what would be refused).
  - The IP range scan has no size cap (an existing limit); the restriction only filters which hosts are probed.
  - The request timeout also ends long downloads and streams (including gRPC and SSE) of that route; leave it at 0 for such sites. The global read timeout was verified on the HTTP/1.1 listener; HTTP/2 enforcement follows Go's `net/http` and was not tested separately.
  - The plain-HTTP (bypass TLS) host path never reported upstream errors to the client (existing behaviour, empty 200); only the 413 and 504 of the new limits are answered there.
  - The admin allow-list does not cover the plugin loopback listener of an HTTPS admin panel (127.0.0.1 only). Plugins that call the admin port itself, and Fleet or cluster peers and API v1 clients, are subject to it and must be listed. The check is on the TCP peer: an admin reached through another reverse proxy that is not Dunree sees that proxy's address.
  - The web terminal restriction was unit tested at the dial and probe level; the full gotty session was not started in tests. The GUI was not driven in a browser here (no UI smoke run).

## Security audit log (dual proxy plan, Phase 2 slice D)
- New dedicated log `conf/security_audit.log` (JSON lines, mode 0600, `mod/secaudit`): time, **actor** (admin user name, `admin` with `-noauth`, `token <name>` for the REST API, `command line` for `-reset_admin_allowlist`), **source address** (the direct TCP peer; `X-Forwarded-For` and friends are deliberately ignored, a header is caller controlled), event, target, outcome (`ok`, `error` for a refused or failed change, `denied` for 401/403) and a redacted detail. Size bound: 5 files x 5 MiB (rotation to `.1` ... `.4`, the oldest file goes, never the entry being written). A write that fails (disk full, bad permission) keeps the entry in a bounded memory queue (1000) and retries with the next entry; the viewer shows a warning while entries are queued.
- Tamper evidence: every entry holds the SHA-256 of the previous one and its own, so an edited, removed or reordered entry is reported by "Check log integrity" (`GET /api/security/audit/verify`). It does not stop someone who can rewrite the whole file and its chain; forward the file off the box for that.
- **What is recorded**, by one middleware in front of the admin API and one in front of the REST API v1 (the same place the change history hooks in, no handler was edited): deployment role (`deployrole.*`), trusted proxies (`trustedproxy.*`), access rules, blacklist, whitelist and quick ban, admin allow-list (`adminallow.*`, also the `-reset_admin_allowlist` flag), destination restriction (`destguard.*`), upstream certificate trust (`upstream.tls.change`: any request that carries a CA bundle, pins or the skip-verify flag, also inside the upstream `payload` JSON), rate limit changes (`ratelimit.change`), the other proxy rule, vdir, timeout, header and auth settings (`proxy.*`), WAF, auto-ban, bot and header rules, SSO, basic auth, **API token create / revoke / delete** (`apitoken.*`, which nothing recorded before), certificates and ACME, ECH, plugins, cluster / Fleet, posture apply / undo, the in-app update start, configuration **import, export and history restore** (`config.*`; export is recorded for GET too because it hands out secrets), and REST API changes (`restapi.*`). Account and sign-in events stay in `auth_audit.log` (mod/auth).
- **Redaction** (by field name, in `mod/secaudit/redact.go`): *never-log* fields are dropped entirely (password, token, secret, API key, cookie, authorization, CSRF, one-time codes, credentials, private key); other secret-looking names (anything containing password, secret, token, credential, cookie, session id, bearer, signature, ... or ending in `key`) keep the key and show `[redacted]`; JSON values (such as `config` and the upstream `payload`) are redacted key by key; a PEM certificate bundle is stored as a count and a fingerprint, a private key block as `[redacted]`; URL passwords and `Bearer` values are masked; control characters are removed; values are cut at 200 characters, at most 32 fields per entry. The listing redacts again on the way out.
- API (admin only, closed for viewer accounts like the history): `GET /api/security/audit/list` (`event` exact or `prefix*`, `actor`, `limit` up to 200, `before` cursor, returns `next` and write statistics), `GET /api/security/audit/verify`. GUI: Security Center > **Audit log** (filter by area and by user, load older entries, integrity check).
- The log is never part of a configuration export, a configuration import cannot replace it (entries named `conf/security_audit.log*` in an archive are ignored) and it is carried over into the new config folder when an import replaces the old one.
- Tests: `mod/secaudit` (actor attribution and spoofed headers, unauthenticated requests not recorded, outcomes, redaction of every never-log and secret case, PEM and JSON, listing that re-redacts a line written elsewhere, rotation bound and mode 0600 with the newest entry kept, reopen resumes the chain, 16 concurrent writers with a verified chain and a complete pagination, tamper and removal detection, write failure queue, filters, token lifecycle, nil logger), main package (`securityaudit_test.go`: real token handlers create / revoke / delete without the token reaching the log or the listing, REST token actor, the Phase 2 settings, viewer closed, verify endpoint, export and hostile import).
- Known limits:
  - Only the settings listed above are recorded. A change made through an endpoint that is not in the route table of `mod/secaudit/http.go` (for example statistics or logging settings) appears only in the change history. The log says that a setting was changed and with which submitted values, not the previous value (the change history has the before / after).
  - The detail is what the request submitted. A request the handler rejected is recorded as `error`, but the admin API mixes success and failure in 200 answers, so the outcome is read from an `{"error": ...}` body; a handler that fails another way reads as `ok`.
  - Uploads (multipart, such as the configuration import) are not read, so the archive name is not in the entry. Only urlencoded and JSON bodies up to 64 KiB are parsed.
  - Requests refused before they reach the admin mux (the admin allow-list, a failed login) are not in this log; sign-in failures are in the auth audit log.
  - The actor of a request is the signed-in account; a `-noauth` instance records `admin` for everyone. The log is not signed with a key, so root on the host can rewrite it.
  - Not verified here: the GUI card was not driven in a browser (no UI smoke run).

## Phase 2 review follow-up: fixes, upgrade notes and known limits
Fixes after an independent review of Phase 2 (each has a test that sends the attack input):
- **Admin allow-list and proxy rules**: the `X-Forwarded-Server` marker check is gone (a client or the hop-by-hop handling could remove it, and WebSocket requests never carried it). Replaced by a dial-time guard on every outbound dialer of the proxy (`mod/adminallow/dialguard.go`), active only while an allow-list is set.
- **Forwarded (RFC 7239)** from a trusted proxy is no longer kept: it is rebuilt from the verified X-Forwarded-For chain plus this hop, so a client cannot inject `for=`, `host=` or `by=` elements through a trusted peer.
- **Header names**: the identity headers are removed in every spelling for untrusted peers (`X_Forwarded_For`, `X_Real_Ip`, `X_Client_Cert_*`, other case forms), and underscore / non-canonical spellings are also dropped when the peer is trusted (a trusted proxy writes the hyphen form). Only active when header hardening is on.
- **Request timeout** is skipped only for genuine WebSocket upgrades; any other `Upgrade` header (h2c, custom) is subject to it. CONNECT stays exempt.
- **Timeout in the middle of a response body** no longer writes a second status line / "Gateway Timeout" text into the stream.
- **Deployment card**: switching back to Standalone restores your own "harden headers" choice; the state the role forces on screen is not saved.
- **Allowed backends**: an upstream written without a port is matched on 80 (443 with "Require TLS" or an `https://` prefix), not "any port". The list is also applied to stream proxy (TCP/UDP) targets when they are added or changed. An upstream update only re-checks the target when the target or its TLS flag changed. Targets that already exist and violate the list (import, history restore, list set later) are never changed; they are shown on the Network exposure page and by the new Security Overview check "Existing upstreams are inside the allowed backend list" (only counted when a list is set).
- **WebSocket upstream TLS**: the rule's SNI / "overwrite host header" name is used for `wss://` verification only when an upstream trust option (CA bundle, pin or client certificate) is configured; otherwise the historical behaviour is kept. (This corrects the slice B note above that said WebSocket now always honours the SNI override.)
- **Viewer accounts** can no longer read `/api/deployrole/get`, `/api/destguard/get`, `/api/adminallow/get`.

Upgrade notes:
- Posture check "No proxy rule points at the admin interface" is a **warning** (not a failure) for existing configurations; it only reads configuration and changes nothing. With an admin allow-list set, such a rule stops working (the dial is refused), by design.
- Header names with underscores are removed from untrusted peers' requests when hardening is on (it is off in Standalone unless switched on). A client that relied on sending `X_Real_Ip` through a hardened proxy loses it.

Known limits (Phase 2 as a whole):
- The admin-allow lock-out check runs in the Set call only. A configuration import or a history restore can install an allow-list that does not contain your address and lock you out of the admin panel. Recovery: stop Dunree, start it once with `-reset_admin_allowlist`, then remove the flag (the sys.db value can also be restored from a backup).
- The peer gate answers `403` to `/.zoraxy/health` for a monitor whose address is not a trusted proxy and not in the direct networks. List the monitor's address under "Networks that may connect directly".
- Virtual directories get no CA bundle or pin (only their existing skip-verify flag).
- The admin allow-list and the dial guard do not cover the plugin loopback listener (127.0.0.1 only, HTTPS admin panel). The dial guard compares the dialled address with the `-port` value and this machine's interface addresses; an admin panel reached through a NAT or port forward on another host is not recognised. Health checks and the uptime monitor are not guarded (they only issue GET requests).
- Allowed backends for stream proxy targets are checked at save time only, like proxy rule upstreams; a name that later resolves elsewhere is not caught.
- The Deployment card change was not run in a browser here (no Node or UI smoke run); it is covered by a source check only.

## CrowdSec bouncer (dual proxy plan, Phase 3 slice E)
Off by default; an existing config or sys.db behaves exactly as before. The first time it is enabled the mode is **Log only**.

- New package `mod/crowdsec`, Security Center > **CrowdSec**: enable, LAPI address, bouncer API key, mode (Log only default / Enforce), ban response (403 page or connection closed), captcha decisions (logged only by default, or the site's existing CAPTCHA challenge when the site has one), pull interval, cache size, longest decision lifetime, grace period, fail-closed, exempt sites, CA bundle and key pins for an https LAPI (no skip-verify). Status card (ok / degraded / down, last successful pull, decisions in memory, LAPI latency, errors, counters, warnings), **Test connection**, recent matches and recent decisions (100 each).
- LAPI usage (documented interface only, cited in `mod/crowdsec/doc.go`): `X-Api-Key`, `GET /v1/decisions/stream?startup=true` then deltas (`new` / `deleted`), `GET /v1/decisions?ip=` for the test. Stream answers are decoded element by element (bounded memory, 128 MiB cap), the cache is replaced only after a complete startup answer, any error forces a full resync with 2 s to 2 min backoff.
- Cache: exact addresses plus ranges (one map per prefix length, IPv4 and IPv6), hard maximum (default 100,000, ceiling 500,000), expiry from `duration` capped by the lifetime setting, `/0` ranges refused, other scopes and types counted and not enforced, ban beats captcha.
- Request path (`dynamicproxy/crowdsec_hook.go`, first thing in `abuseBegin`, so every listener and the default site are covered): the address is `GetClientIPForEndpoint` (the same trusted-proxy aware resolution as rate limits and ACLs). Blocks are recorded in the blocked-request log with the reason **CrowdSec** (new `Reasons()` entry, statistics count them as blocked). Loopback, this server and trusted proxies are never acted on.
- Fail-open (default) or fail-closed when the LAPI has been unreachable longer than the grace period (counted from enabling when there was never a successful pull). Fail-closed needs `confirmfailclosed=true` on the API (the GUI asks), only acts in Enforce mode and the card shows a warning while it refuses traffic.
- API key: sealed (AES-256-GCM, per-install master key, mode 0600) in `conf/crowdsec/`, same scheme as the AI assistant key; excluded from configuration exports; never returned (only `keySet`), never logged (errors never quote response bodies and are scrubbed), `apikey` is a never-log field of the security audit log. Settings: sys.db `settings/crowdsec`.
- API (admin session + CSRF, all closed to viewer accounts): `GET /api/crowdsec/get`, `POST /api/crowdsec/set` (`config` JSON, `apikey`, `clearkey`, `confirmfailclosed`), `POST /api/crowdsec/test`, `GET /api/crowdsec/status`, `GET /api/crowdsec/decisions`. Set and test are recorded by the security audit log (`crowdsec.set`, `crowdsec.test`) and by the change history ("CrowdSec settings changed"). The LAPI destination is resolved once and checked with `destguard.Classify` at save, test and dial time: cloud metadata, link-local, multicast, unspecified and reserved addresses (also in IPv4-mapped / NAT64 form) are refused, loopback and private ranges are allowed (the LAPI is admin-defined and normally local). Redirects are not followed.

## Rate limit identity check and hardened security headers (dual proxy plan, Phase 3 slice F)

### Rate limit identity (verification, no behaviour change)
- Read and tested, not changed: the host level rate limit (`dynamicproxy/ratelimit.go`) keys its buckets on `GetClientIPForEndpoint` (rule's trusted-proxy gate), the Status page "Tune" sampler (`livetune.go`) only reads those buckets' counters and never resolves an address itself. Other consumers (ACL, CrowdSec, abuse, CAPTCHA, WAF) use the same function.
- New tests (`dynamicproxy/ratelimit_identity_test.go`, through the real listener entry plus the limiter): an Internal proxy behind an External one limits each real client separately and never creates a bucket for the front proxy address; forged left-hand `X-Forwarded-For` / `X-Real-IP` / `CF-Connecting-IP` / `Forwarded` values rotated on every request through a trusted proxy do not escape the limit (Internal, External, Standalone with hardening on); an untrusted peer that rotates spoofed headers stays in one bucket (its TCP address) in all four modes; garbage identity values fall back to the peer instead of failing open.
- **Requirement found (warning added, behaviour not changed)**: every consumer reads forwarded headers only on access rules that have **Enable Trusted Proxy Gating** on (and only from a trusted peer). With the rule's gating OFF, even in the Internal role the limiter keys on the connecting front proxy, so all visitors share one bucket (asserted by a test). Making the roles override the rule would change existing rules, which the plan forbids, so instead Security Center > Deployment now warns ("Some access rules do not have Trusted Proxy Gating...", and the API lists them in `ungatedRules`) when headers are hardened, the trusted proxy list is not empty and any access rule has the gating off. Test: `TestDeployRoleWarnsAboutUngatedAccessRules`.
- **Known limit, not changed (a default change)**: in **Standalone with "Harden forwarded client address headers" OFF**, a rule that trusts proxy headers believes `X-Real-IP`, then `CF-Connecting-IP`, then the **first** `X-Forwarded-For` entry sent by a trusted peer. A trusted proxy that appends to a client supplied `X-Forwarded-For` (instead of replacing it) lets a client choose its own rate limit bucket (and its address in ACLs and bans). A test asserts this so a change is noticed. Fix: turn the hardening on (role External / Internal, or the opt-in in Standalone), which uses the right-most untrusted hop.

### Hardened security headers preset
Off by default, per site and as a global default for new sites. An existing config has no new key and sends no extra header (tested: no `HardenedHeaders` key is written for a rule that does not use it).

- Edit site > **Security** > "Hardened security headers" (Advanced mode; shown in Easy mode only when on). The card saves by itself (like Header rewrite rules) and shows a live table "Headers that will be sent" with, per header, whether it is *added only if the upstream sends none*, *replaces the upstream value*, or *not sent* and why. Options: HSTS (max age 1 month to 2 years; `includeSubDomains` and `preload` only when ticked, preload needs includeSubDomains and at least 1 year), `X-Content-Type-Options: nosniff`, `Referrer-Policy` (four values), framing (`X-Frame-Options` DENY / SAMEORIGIN, or CSP `frame-ancestors 'none'` / `'self'`), `Permissions-Policy` (camera, microphone, geolocation, payment, USB, motion sensors, MIDI, serial, HID, display capture and interest-cohort off; every other feature stays allowed; built with `mod/dynamicproxy/permissionpolicy`), and "Replace values the upstream already sends".
- Global default for new sites: Network > Listeners > "Security headers for new sites" (same editor). It is applied once when a proxy rule is created through the add-rule API (`ReverseProxyHandleAddEndpoint`), after any template, and never to a rule that already has its own setting. Existing rules are not changed.
- Precedence, highest first: headers the admin set on the site (custom header rules in the downstream direction including "remove" rules, the site's own HSTS switch, the site's own Permission Policy switch), then what the upstream sent, then the preset. With "Replace values the upstream already sends" the preset also replaces upstream values, but never an admin header, and never edits an upstream `Content-Security-Policy`: a `frame-ancestors` policy is added as a second CSP header only when the upstream's policy has none (a second policy can only add restrictions).
- HSTS is only sent on requests that arrived over TLS. Applied to proxied responses of the TLS path and virtual directories (`dpcore.injectHardenedHeaders`, before the custom headers).
- API: `GET/POST /api/proxy/header/hardened` (`domain`, `settings` JSON; GET with `settings` only previews), `GET/POST /api/securityheaders/default` (same JSON). Both validate (unknown fields, bad Referrer-Policy / framing values, HSTS age 300 to 63072000, preload rules) and refuse bad input without saving. The per-site save is recorded as `proxy.header.hardened` in the security audit log and in the change history (rule JSON); the global default as `securityheaders.default`. `/api/securityheaders/` is closed to viewer accounts; a viewer can still read a site's own setting like its other header settings, but cannot save. CSRF as for the sibling endpoints.
- Tests: `dynamicproxy/hardenedheaders_test.go` (off by default and no JSON key, HSTS options only when chosen, 10 invalid inputs incl. header injection, admin precedence, end to end through the real proxy handler with an upstream that sets its own `X-Frame-Options` and CSP: off / fill gaps / override / CSP handling / admin wins / HSTS only over TLS), `dpcore/hardened_test.go`, `hardenedheaders_api_test.go` (default off, new site only, never overrides a site's choice, persistence, bad input leaves the stored value, damaged stored value ignored, preview does not save), secaudit event names and viewer denial.
- Known limits:
  - Not applied to responses Dunree generates itself (block pages, error pages, CAPTCHA pages), to WebSocket / CONNECT / upgrade tunnels, or to the plain-HTTP (bypass TLS, port 80) host path, which also ignores custom response headers today (existing behaviour, not changed here).
  - Behind a TLS-terminating proxy that talks plain HTTP to Dunree, Dunree does not see TLS and sends no HSTS (it does not read `X-Forwarded-Proto` for this); turn the preset on at the proxy that terminates TLS.
  - HSTS and preload are sticky in browsers for the chosen age. The preset gives no warning about subdomains that cannot do HTTPS.
  - The Edit site card is driven by `tools/ui-smoke/crowdsec_smoke.py` (off by default and no header sent, preview, save, headers really sent over https, an upstream `X-Frame-Options` kept, invalid input refused, dark and 390 px layout). That run found two GUI bugs, fixed: the switches in the card did not react to a click on their label text (Fomantic checkboxes were not initialised in the frame), and the preview table squeezed the Header column. The Listeners control (global default for new sites) is still checked by `extract.py --check` only.
  - Not checked: whether Fleet / cluster sync carries the new rule field (it is part of the rule JSON, but the sync allow-list was not read), and whether the change history lists the per-site save by name (the saved rule file is the same one the other header settings use). The global default is a sys.db setting and does not travel.

## Configuration management and reliability (dual proxy plan, Phase 4 slice G)
Audit findings 5 and 6 of `docs/enterprise-dual-proxy-plan.md` (section 9). Everything is opt-in or additive: `/api/conf/export` without parameters is still the full backup, old exports still import, and the only default that moves is the one finding 6 asked for (stopping now drains).

### Export (Utilities > System Backup & Restore > Open Config Tools)
- Two modes. **Full backup** (default, unchanged content) is now labelled **contains secrets** in the UI: TLS private keys, the cluster secret, Fleet keys, notification secrets, basic-auth hashes (the database option adds DNS-provider credentials, OAuth secrets, API tokens). **Shareable (redacted)** is `GET /api/conf/export?mode=shareable`.
- Shareable is an allow-list (`proxy`, `redirect`, `access`, `streamproxy`, `rules`, `ruleset`, `abuse`, `trusted_proxies.json`, `acme_conf.json`, `waf_central.json`, `plugin_groups.json`, `log_conf.json`, `blocklist_sources.json`, `botrules.json`, `sitelog.json`, public certificate files, `version`) plus an explicit never-export list that wins over it: `cluster.json`, `.cluster/*`, `notify.json`, `waf_challenge.key`, `crowdsec/`, `aiassist/`, `ech.json`, `zrok.json`, `webui/`, `sso/`, `basicauth_lists.json`, history and audit logs, every `*.key`, any file whose name looks like a secret store, and any file containing a `PRIVATE KEY` block. The system database is never included (API tokens and sessions live there). Anything else in the config folder (statistics, visitor data, GeoIP files) is simply not part of it.
- Inside the JSON files that are included, credential fields are replaced by `[REDACTED]` by key-name rules (`password`, `secret`, `token`, `apikey`, `privatekey`, `credential`, `authorization`, `cookie`, ... plus an explicit list), by value (PEM private keys, bcrypt/argon hashes), by header pair (`{Key:"Authorization", Value:...}`) and passwords inside URLs. Only non-empty strings, objects and arrays are replaced, so `"UseToken": false` and the file shape survive.
- The shareable export always contains `manifest.json`; the full backup only with `&manifest=true` (checkbox in Config Tools), so that by default it keeps the historic layout an older Dunree can restore. The manifest has: `format`, `schemaVersion` (1), `configSchema`, `zoraxyVersion`, `mode`, `created`, `includesDB`, every file with `size` and `sha256`, and for shareable the `excluded` list (names and reasons, never content).

### Import
- New **Check file (dry run)** button (`POST /api/conf/importcheck`): validates the archive and reports what would be added, replaced, removed and kept, whether it is verified, and changes nothing (also no history snapshot or audit entry for the check itself). **Restore & Exit** is enabled after a successful check.
- Validation happens before anything is written: entry names (zip-slip, absolute paths, drive letters, backslashes, NUL, `.`/`..`/empty segments, symlinks and other non-regular members, duplicates also by case), entry count (20 000), per file size (1 GiB), total size (2 GiB) and upload size (about 2 GiB), checked against the declared sizes and again against the bytes really produced; JSON files (up to 16 MiB each) must parse; proxy rules need `RootOrMatchingDomain`, access rules need `ID`. With a manifest: format, mode and schema version, and every entry must be listed with a matching size and SHA-256 (an unlisted or missing file is refused). **A manifest whose schema version is newer than this build (or whose config schema is newer) is refused.** A shareable archive that contains anything a shareable export never carries is refused.
- Archives without a manifest (created by older builds) still import; the dry run says **unverified**.
- Atomic apply: files are written to `<conf>.staging_*` next to the config folder, then two renames: live folder to `<conf>.old_<unix>` (the automatic backup, as before) and staging to live. Any failure after the first rename puts the old folder back; the system database is staged the same way and swapped last (old file kept as `<db>.pre-import_<unix>`), and a failure there rolls the config swap back too. The audit log is never replaced or erased (as before).
- **Importing a shareable archive never deletes secrets**: the live files a shareable export cannot carry (cluster, Fleet, notify, keys, vaults, basic-auth lists, existing certificate files ...) are kept; a `[REDACTED]` field keeps the value the same JSON path has on this install and is dropped when there is none, so the marker never reaches a live rule. Rule files that are in the archive replace the live ones and rule files that are not are removed (like a full import).
- Audit log (`mod/secaudit`): `config.import.result` with outcome `ok` / `error` / `denied` and mode, verified, counts, backup folder (plus the existing automatic `config.import` / `config.export` entries). The dry run is not recorded.
- Permissions: staged files are 0600 for keys, `.cluster`, `cluster.json`, `notify.json` and certificate PEMs, 0644 otherwise (the old restore used the process umask for everything).
- Viewer accounts: `/api/conf/import` (and `importcheck`) added to the denied prefixes next to `/api/conf/export`.

### Config schema version and migrations
- `conf/config_schema.json` (`{"schema":1,...}`) is written at startup by `confpack.Migrate`; a registry (`confpack.Migrations`, none yet) runs steps in order after copying the config folder to `<conf>.premigrate_<from>_<unix>` (without `.history` and `geodb`). A stamp-only upgrade changes no data and takes no copy. A failing step leaves the stamp unchanged so the next start retries; running again at the current version does nothing. A folder stamped by a newer build is left untouched with a warning in the log. Imports carry the stamp inside the archive (and the manifest's `configSchema`).

### Fleet
- **Certificates scope and captured keys send TLS private keys.** The API now refuses to newly enable them without an explicit `ackCerts=true` (`groupSet` and `nodeScopes` with the `certs` scope, `settings` with `captureCerts=true`) or, for the legacy primary, `ackSyncCerts=true` on `/api/cluster/config` (`syncCerts=true`). The UI shows a standing note and a confirm dialog; every acknowledgement is a hub audit entry (`certs.ack`). Saving something that is already on, or turning it off, needs no flag (existing setups keep working).
- **Drift detection.** Nodes now report one hash per managed scope in their heartbeat (new field `scopeHashes`); the hub computes the same hashes from the bundle it would send that node (variables resolved) and shows **in sync / drifted: proxy, access** (`syncState`, `driftScopes`, `driftReason` in the overview, a line under the version in the node table). Only non-secret material is hashed: file paths plus, for JSON, the document with credentials redacted by the same rules as the export and keys sorted; private keys contribute only their path. Hashes are 64 hex characters, at most 24 scopes per heartbeat. A credential-only edit on a node is therefore not named as a scope (the old "managed files were edited on the node" flag, which hashes whole files, still raises drift for it). A node on an older build reports no hashes and shows the previous behaviour (`syncState: unchecked`).

### Graceful stop
- `-shutdown_drain <seconds>` (default **8**, capped at 15 on the SIGTERM / restart path and 10 for the updater, `0` = stop at once, the old behaviour; see the review follow-up below). SIGTERM/SIGINT, the Fleet / history restart path (`clusterReload`, `historyReload`) and the updater hook now close the proxy listeners first (no new connections) and let in-flight requests finish for at most that long on the main, HTTP/3, port 80 and secondary listeners; after the deadline remaining connections are closed. Then every other step (history, stats, mDNS, databases, logger ...) runs with a 3 s limit each and an 8 s overall budget; a hung module is abandoned and logged instead of hanging the stop. **A second signal while stopping exits immediately (status 1).** `ShutdownSeq` is safe to call twice (signal plus restart): the second caller waits for the first.
- The updater waits 20 s for its hook, so `ShutdownSeqForUpdater` caps the drain at 10 s (10 + 8 = 18 s). `restartSelf` (unix `exec`, windows `exit`) is unchanged and still runs after `ShutdownSeq`.
- Listener restarts from the admin UI (`StopProxyService`) keep their old 10 s / 5 s limits.

### Upgrade notes
- A stop now takes up to 8 s longer when a request is still running (previously it was cut at once); worst case 28 s (see below). The shipped unit's `TimeoutStopSec=30` and `docker stop` (10 s) are covered because state is checkpointed before the drain. Use `-shutdown_drain 0` for the old behaviour.
- A full backup is byte layout compatible with older builds unless `manifest=true` is asked for; an archive with `manifest.json` (shareable, or full with the flag) is refused by an older Dunree ("invalid zip file structure"). Newer builds import archives of older ones.
- An import of a damaged or hand edited proxy / access JSON file is now refused (it used to be written blindly).

### Known limits
- Not run in a browser: the new Config Tools layout, the Fleet confirm dialogs and the drift line are covered by source checks and `extract.py --check` only (no Node here, full UI smoke is run by the lead). Light/dark/390 px layout is unverified.
- The shareable redaction is by field name, string shape and header pair; a secret stored under an innocuous name in a free-text field is not found. Review a shareable archive before publishing it; `manifest.json` lists every file and the number of redacted fields.
- Hijacked connections (WebSocket and other upgrades) are not tracked by `net/http` and are closed when the process exits (best effort, not drained). The admin listener has no drain of its own (it is a plain `http.Serve`); an admin request in flight at SIGTERM is cut after the proxy drain.
- A system database import still closes the database, replaces the file and exits after 3 s (unchanged); if the swap fails after the database was closed, the old files are restored and Dunree exits to reopen them. This path was only tested with injected failures, not against a real bolt database file.
- The apply renames need the config folder and its parent on the same filesystem and the parent writable (a config folder that is itself a mount point cannot be renamed; the import then refuses and changes nothing).
- Drift compares the files a node manages. It does not see node local files in a merging scope, extra (non file) scopes, or secret-only edits (see above). The hub recomputes the desired hashes per overview refresh (memoised per version / selection / node).
- A second concurrent import returns 409. The dry run reads the uploaded file fully (including checksums), so a 2 GiB archive takes as long to check as to stage.
- The drain tests for secondary and port 80 listeners use a hand wired listener for the secondary case; the real `startSecondaryListeners` path shares the same shutdown code but is not driven end to end by a test.

Two new Security Center tabs. Nothing changes for an existing install: the Overview only reads, and the Network plan does nothing until a plan is saved.

**Overview** (`GET /api/security/overview`, one request, cached 5 s, refreshed every 10 s only while the tab is visible). - UniFi and Proxmox text is generated from documentation and is untested against real devices; menu names differ between versions. The browser check (light, dark, 390 px) was done on a throwaway instance; the full UI smoke was not run.

## Phase 4 review follow-up: fixes, changed behaviour and known limits
Three reviewers read the Phase 4 work. Every finding was checked against the code; this is what changed (each fix has a test) and what did not.

### Import and export (src/mod/confpack, src/confbackup.go)
- **A shareable archive can no longer set credentials.** On import every field the redactor would have replaced (by name or content: passwords, hashes, tokens, `RemoteTokenHash`, URL userinfo, secret query parameters ...) is forced back to the marker first, so the live value stays and a real looking value in the archive is ignored. The dry run counts them (`secretsIgnored`) and warns; the audit entry `config.import.result` carries `credentialsIgnored`. Arrays of objects are matched to the live ones by an identifying field (`ID`, `Name`, `Username`, `RootOrMatchingDomain`, `Domain` ...), not by position, so a reordered array cannot move one element's secret into another; an element without a live counterpart gets none. Elements that have no identifying field are still matched by position.
- **The manifest proves integrity, not authenticity.** The dry run no longer shows a green "Verified"; it says "Integrity checked, not authenticity" (blue) because an attacker can build a self consistent manifest.
- **More redaction.** Field names containing `token`, `hmac`, `webhook`, `dsn` (apiToken, botToken, HmacKey, RemoteTokenHash, webhook URLs ...), numbers under secret looking names (except sizes, times and switches such as `TokenTTL`), URL userinfo without a password (`https://TOKEN@host`) or with `@` in the password, and `?token=` style query values. A name based filter can still miss a secret stored under an innocuous name.
- **Permissions.** Staged files keep the mode of the file they replace; new ones are 0600 when they can hold credentials (system database, proxy rules, certificates, `acme_conf.json`), 0644 otherwise. A new `sys.db` is 0600.
- **Audit logs.** `auth_audit.log` (login and session audit) joins `security_audit.log`: never exported by the full backup (a change: it used to be included) and never replaced or erased by an import.
- **`version` and `config_schema.json`** are never taken from a shareable archive (the live ones are kept), so an archive cannot make migrations run again or be skipped.
- **Rule files with secret looking names** (`proxy/token.example.com.config`, `private.corp...`) are exported (their content is redacted by field) and importable; the by-name filter stays for other files and any `.key`. Certificates are checked by content.
- **Entry names**: control characters (also U+2028/2029) are refused, every archive derived name in an error is quoted. On Windows also reserved device names, `:` and trailing dots or spaces. They are not refused on other platforms because an old install may hold a rule named `host:8080.config`.
- **The full export keeps the historic layout** (no `manifest.json`) unless `manifest=true`; see the upgrade notes above. A half written `config_schema.json.tmp` is not exported.
- **Restore safety**: the change history (`.history`) is carried into the restored folder; a symlink in the live folder is reported in the dry run (it stays only in the `.old_` backup); a rollback that cannot complete says where the previous configuration is, and copes with a module that recreated the folder between the two renames. Any import now reports `restartRequired` (the running process keeps its settings in memory and can write them back); the dialog says so and shows the backup folder. The process still restarts by itself only when the system database was replaced.

### Fleet
- Moving a node into a group that carries the `certs` scope (`nodeGroup`), or clearing a node override so it inherits one (`nodeScopes` with `inherit=true`), needs `ackCerts=true` like the other ways in, and is audited as `certs.ack`. **Breaking for API scripts that enabled certificate sync**: they must send `ackCerts=true` (hub) or `ackSyncCerts=true` (legacy primary); the UI does. An old cached UI bundle gets the plain error text until it is reloaded.
- Drift: a scope the hub ships but the node has not reported is "unchecked", not drifted (upgrade window). A converged node with a node local file is covered by a test.
- The drift hash note was too strong: files that are not JSON are hashed whole and an unredacted secret field stays in a JSON hash, and an unsalted SHA-256 can be guessed against by whoever sees the heartbeat (the hub operator). Keep secrets out of managed files. A per cluster keyed hash is a follow-up.

### Stop
- **Default drain is 8 s** (was 15 in the unreleased first cut), capped at 15 s on SIGTERM; the updater cap stays 10 s. Worst case: 2 s checkpoint + 15 s drain + 3 s guard + 8 s steps = 28 s (the unit's `TimeoutStopSec` is 30).
- **State is checkpointed before the drain** (blocked request log, visitor list, statistics summary, bandwidth counters), so a SIGKILL during the drain loses almost nothing. Sessions and the rest still close in the later steps.
- Once the stop begins the router refuses `Restart`, `StartProxyService` and `UpdateSecondaryListeners` (`ErrProxyStopping`), so an admin or Fleet action cannot re-bind a listener while modules close.
- A force quit (second signal) tries to close the system database for at most 1 s. Late log lines after the logger closed go to the standard logger. The mDNS step (which can block on a scan) runs last so it cannot starve the steps that save state.

### Dashboard
- URLs and error strings in the Security overview (monitor URLs, CrowdSec last error, evidence) are scrubbed of URL userinfo, secret looking query values and bearer tokens.

### Known limits (not done)
- No golden test over every real config struct (only a list of field names seen in the code); a new secret under a new name must be added to the redaction rules or it is exported.
- Steps abandoned after their 3 s limit can still be writing while later steps run; the stores are not atomic (temp file and rename) yet.
- Heartbeat hashing is not memoised by mtime and the hub builds scope hashes per node on a cold cache; fine for tens of nodes.
- A conf-only import does not restart the process; restart it yourself (the report says so).
- Only English was added to the catalogue; the other locale files have no entries for the new strings (the UI falls back to English).
- The overview rebuild copies and scans the whole block log ring every 5 s at most (cached, bounded); no build timeout.

## Enterprise baseline (safe settings on by default for new installs, one button for existing ones)

Code: `src/mod/baseline` (bookkeeping, fresh-install detection), `src/baselineapi.go` (items, API, startup hook), Security Center > Overview (card at the top), palette entry "Enterprise baseline".

### What it does

* **Fresh installs** start with the baseline already applied (at the first start only).
* **Existing installs are not changed by an update.** The Overview card shows the status of each item and an "Apply enterprise baseline" button. The button opens a preview (current value -> new value per item, and the reason for every item it will not touch) with the statement that nothing that blocks traffic is changed. After an apply an **Undo** button restores the previous values.
* The card lists every item with on/off, why it matters, what the baseline does and the one thing to know, and a link to the tab where it is changed.

### The items, and why exactly these

| Item | In the baseline | Decision |
| --- | --- | --- |
| Security audit log | shown only | Already always on (there is no switch; it only stays off when the log file cannot be opened). Shown as "Recording" so it is visible. |
| Forwarded client-address header clean-up (deployment "harden headers", standalone role) | changed | Headers such as X-Forwarded-For are only believed from proxies on the Trusted Proxies list. Blocks nothing. **Effect behind an unknown proxy:** if this Dunree sits behind a proxy or CDN that is not listed, that proxy's client address and X-Forwarded-Proto/Host are ignored and sites see the proxy's address. Therefore: on a fresh install it is applied (no site exists yet, and the Deployment tab already warns when the list is empty); on an existing install the button applies it **only when the trusted proxy list is not empty**, otherwise the preview shows it as not applied with that reason. It is never applied when the role is external or internal (the role manages it). |
| Default security headers for sites created later | changed | Writes the existing "security headers for new sites" default: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security` for 30 days on HTTPS requests only (no includeSubDomains, no preload; short enough to recover from a certificate mistake). Per-site settings of existing sites are never read or written; a site that has its own choice keeps it. If the administrator already has an enabled default, it is left alone. **Left out on purpose:** frame blocking (breaks embedding) and `Permissions-Policy` (the existing preset sets camera, microphone, geolocation, display capture and more to none, which breaks video calls, maps and screen sharing; the preset has no "minimal" variant, so it is excluded rather than changed). |
| CrowdSec | shown only | Cannot be enabled by a baseline: it needs the LAPI address and an API key. The card shows "Not configured" with a Configure link. Once configured, the existing log-only-first behaviour applies. |
| Destination guard for diagnostic tools (cloud metadata and link-local) | **excluded** | `RestrictTools` also refuses loopback addresses for the uptime monitor, port tools and web SSH, so a backend on `127.0.0.1` would show as down. It cannot be limited to metadata/link-local without a code change, so it stays an explicit choice under Network exposure. |

**Never in the baseline:** internal peer gate, admin allow-list, role changes, fail-closed CrowdSec, enforce mode, rate-limit enforcement, destination allow-lists, anything that blocks traffic or restricts admin access. The tests assert that these settings are not written.

### Fresh-install detection and the stored state

`CaptureProbe` runs in `main()` before the config schema migration and before the database is opened (both create files) and only reads. A start is a new install only when **all** hold: no `sys.db` (file or folder), no `config_schema.json` stamp, and no regular file anywhere in the config folder (proxy rules, certificates, settings, anything). An unreadable stamp or folder, a database error, an older stamp with no proxy rules, or any file at all means "existing". Any doubt is existing.

The decision is stored once in `sys.db` (`settings/baseline`): `{decision, decidedAt, appliedAt, source: fresh|button, undoneAt, items: {id: {previous, applied}}}`. Later starts read the stored decision and never decide again, so a restart after an undo does not re-apply the baseline. Only items that were really changed are recorded; an item that already had the baseline value is not recorded and Undo never touches it.

### Apply, preview and undo rules

* The preview and the apply use the same plan, so the preview is exactly what apply does. Apply is idempotent: with nothing left to change it writes nothing and records no audit entry; the recorded previous values of an earlier apply are kept.
* Apply is all or nothing: if one item fails or the state cannot be saved, the items already set are put back. The result, the card and the audit entry then report nothing as changed (outcome "error", `changed` 0, the error text in the audit detail). If an item cannot be put back, the error names it and it stays recorded, so Undo can still revert it.
* A failed apply on the first start of a new install is logged ("the first-start apply failed, nothing was changed") and audited as `baseline.apply` by `system` with outcome `error`; the decision stays stored (no retry on later starts) and the button on the Overview card is the way to retry.
* The card rows, the preview and the button use one rule (button-time eligibility), so a row never says "Off" while the preview says "not applied". The preview drawer is loaded from the server when it opens, and the card refreshes every 10 seconds. The header badge is green only when every changeable item is on; otherwise it reads "{on} of {total} settings on".
* A default for new sites that is already stored, enabled or explicitly off, is the administrator's choice: the baseline skips it.
* **Fresh install behind a proxy or CDN:** the forwarded-header clean-up is applied on a new install even though Trusted Proxies is still empty (a directly exposed Dunree is the common case, and a new install has no sites yet). If a proxy or CDN is in front, every visitor then appears with the proxy's address and X-Forwarded-Proto/Host are ignored until the proxy is listed. The first-start log line and audit entry (detail `warning`) say so, and the card shows a warning for as long as the clean-up is on and the list is empty.
* Undo decides ownership by value: if the administrator turned an item off and on again, or saved identical values, Undo still reverts it. It only happens when the administrator presses Undo.
* The first start of this build over an existing install writes one bookkeeping row (`settings/baseline`, decision "existing"). Because the settings table is tracked by configuration history, that can show as one extra history version; no setting changes.
* Undo restores an item only while it still holds the value the baseline wrote. An item the administrator changed afterwards is left as it is and reported ("changed since the baseline was applied"). Undo with nothing recorded is an error, not a silent success.

### API

`GET /api/baseline/get` (items, preview, state), `POST /api/baseline/apply`, `POST /api/baseline/undo`. Admin session and CSRF like their siblings, **closed for viewer accounts** (`/api/baseline/` in `viewerDeniedPrefixes`). Audit log: `baseline.apply` (detail `source` = `fresh` for the automatic one with actor `system`, `button` for the button, `changed`, and `items` with old -> new) and `baseline.undo` (restored items and the ones left as they are). A fresh install shows its `baseline.apply` / source `fresh` entry in Security Center > Audit log.

### Known limits

* The configuration history does not label the baseline route; the change shows as the individual settings (deployment settings, header default) when the history picks them up. Undo is the baseline's own way back.
* A fresh start that crashed before the decision was stored is treated as existing on the next start (conservative).

## Statistics: referring sites without a referrer are sorted by reason

Statistics > Referring sites showed one line "Unknown or hidden" for every request that came without a `Referer` header.
That line is gone. Dunree still stores the header as it is sent (markup removed, cut at 256 bytes), and now also records **why**
it is missing, read from other headers of the same request (`mod/statistic/referer.go`, always on, no setting):

| Shown as | Stored key | When |
|---|---|---|
| a referring site | the `Referer` header | the header was sent (markup removed, cut at 256 bytes; a value that then starts with `~` is stored with `%7E`) |
| a referring site with the tag "Origin header" | `~origin:https://host` | no `Referer`, but an `Origin` header that names another site |
| Direct and apps | `~direct` | `Sec-Fetch-Site: none`: typed address, bookmark, link opened from an app |
| Hidden by policy | `~hidden-policy` | `Sec-Fetch-Site: cross-site`: came from another site that withholds its address |
| Same site | `~same-site` | `Sec-Fetch-Site: same-origin` / `same-site`, or an `Origin` equal to the requested host |
| Bots and scripts | `~non-browser` | no `Sec-Fetch-*` header at all and a User-Agent that is empty, a bot or a library |
| Not sent (reason unknown) | `~unknown` | none of the above |
| Unreadable referrer | `~invalid` | a `Referer` was sent, but nothing is left once markup is removed (e.g. `<script>x</script>`) |
| Unknown (recorded before this version) | empty key | days saved by older versions |

The card lists real sites first, then the reasons with their count and share of all requests, and a note on why a
browser may send no referrer. The CSV export writes the same readable names instead of an empty field.

Also fixed: a rule (`set` / `remove request header`) or a request script that changed `Referer`, `Origin`,
`User-Agent` or a `Sec-Fetch-*` header on the way to the upstream also changed what the statistics recorded. The
statistics now use what the client sent (`mod/dynamicproxy/statsource.go`).

A `Referer` header cannot pose as one of these keys. Markup is removed first and the check runs on what is left
(`StoredRefererKey`, called by `RecordRequest`): a value that starts with `~` is kept only when the removal changed
nothing and it is exactly a key the classifier produces (for `~origin:` the rest must pass the Origin checks). So
`<b></b>~direct` is listed as the referrer "~direct", not counted as a direct visit, and
`<i></i>~origin:javascript:...` is not listed with the "Origin header" tag.

### Known limits
* The card is not a full log: requests that match no proxy rule and rules with statistics off are not counted, the
  per-day cap on distinct values drops rare referrers, and the card lists the top 100.
* "Bots and scripts" is decided by the User-Agent, only when no `Sec-Fetch-*` header was sent. "bot" counts at the end
  of a word (`Googlebot/2.1`, `bingbot;`), so a CUBOT phone is not taken for a bot. The other marks (`scan`, `node`,
  `feed`, `probe`, `preview` and so on) are plain substrings; a device or app whose User-Agent holds one of them is
  counted as a bot when it sends no `Sec-Fetch-*` header (plain HTTP).
* CSV export: the readable names hold no comma (`Direct visit (typed / bookmark / app)`), because the referrers of a
  day are joined with `,` in one cell. A real referrer URL that itself holds a comma still splits (unchanged).
* A header that was never sent cannot be recovered. "Hidden by policy" says that a visitor came from another website;
  which one is known only to that website and the visitor's browser.
* Browsers send `Sec-Fetch-*` headers only over HTTPS (and Safari only since 16.4). Browser requests over plain HTTP
  without a referrer therefore show as "Not sent (reason unknown)". A bot that imitates a browser User-Agent lands there too;
  over HTTPS that row is mostly such bots, and the row text says so.
* New data stored: for requests without a `Referer`, the scheme and host of the `Origin` header (no path, no query, no
  client address). Values that are not a plain http(s) origin are not stored.
* Old days keep the empty key; they are not re-classified. Today's summary can hold both until the day ends.
* The row names are English until the locale files are updated.
* Not changed here: requests that match no proxy rule (and rules with statistics switched off) are not counted at all.
* Changed with it: a request whose upstream was down was counted twice (once as the error, once more as a success with
  status 502) in the statistics and the access log. It is counted once now, so the totals of sites with a failing
  upstream are lower than before and the success share is no longer inflated.
* Tests: `mod/statistic/referer_test.go`, `mod/dynamicproxy/statsource_test.go`, `mod/statistic/analytic/sites_test.go`
  (CSV names), UI: `tools/ui-smoke/certs_traffic_smoke.py` (Statistics part), 1366 px light and dark and 390 px.

With rejecting on, HTTPS access by IP address or under any name without a rule stops working (the default site included) and such clients see a TLS error, not an error page; a rule for an IP address keeps working only when that address is a local address of this server (behind NAT, a port forward or a Docker port mapping the connection arrives on another address and is refused too), and then every client without SNI on that address gets the fallback certificate again; the ECH public name needs its own valid certificate or a proxy rule, otherwise clients falling back to it are refused too; refused handshakes show only in the fallback list and its counter, not in the request log; the switch is per node (not part of Cluster / Fleet sync) and has no per-listener or per-name exceptions. Real browser interop (Chrome / Firefox against a published HTTPS record, their GREASE and retry behaviour) was not tested here and stays with the owner; the tests use Go's TLS client, python and `openssl s_client`. Tests: `mod/dynamicproxy/ech_result_test.go`, `mod/dynamicproxy/ech_wiring_test.go` (the real main and secondary TLS listeners), `mod/tlscert/rejectsni_test.go`, `mod/info/logger/echfield_test.go`, `mod/info/logviewer/echfield_test.go`, `src/echlog_test.go`, UI: `tools/ui-smoke/ech_fallback_smoke.py` (`smoke.py --ech-fallback-only`, parts 5 and 6), light, dark and 390 px.
* **Header rules: the missing options (#245)**: Security Center > Header rules got the rest of the request. Per rule: the "The header must" list has three "must not" choices (**be absent**, not equal any of the values, not match any of the patterns; stored as `Negate`), "Otherwise" has **answer another status code** (400 to 499 or 503, stored as `StatusCode` with the deny action; the answer is a short plain text line, not the 403 block page), and a tick box **Remove this header before the request is forwarded** (`Strip`) keeps a shared secret away from the backend. Per site, below the rules: **A request must pass** every rule (default) or **at least one rule** (`HeaderRulesMode: "any"`, OR across headers), and **Addresses that skip the check** (`HeaderRulesExcept`, addresses or CIDRs, one per line). API: `/api/headerrules/set` takes the optional `mode` and `except`, `/api/headerrules/get?meta=true` returns `{Mode, Except, Rules}`; the plain read is still the list. Everything is off by default: a stored rule without the new fields means what it meant before and is written back without them. Validation fails closed: an unknown mode, a status code outside the range, a status code on a non-deny action, an unreadable address or an exception list that matches every IPv4 or every IPv6 address (`/0`, or in pieces such as `0.0.0.0/1` plus `128.0.0.0/1`) is refused on save, and such a value in a hand-edited config makes the site answer 503 instead of opening it; the page then shows a notice above the rules that names the reason (`Invalid` in the `meta=true` answer), and saving the page repairs it. When the last rule of a site is removed, its mode and exceptions are removed with it (also when the API call still sends them), so rules added later start from "every rule" and no exceptions. Secrets of "not equal" rules are masked like the others. Tests: `mod/dynamicproxy/headerrules_opts_test.go`, `TestHeaderRulesAPIOptions` (`headerrulesapi_test.go`), `TestRulesetMigrationProposals`, `tools/ui-smoke/smoke.py --headerrules-only`. Found on the way and fixed: the request log read the request's headers from its background goroutine while the proxy was still changing them, which could end the process with "concurrent map read and map write"; the line is now put together from values read before the goroutine starts (`TestLogHTTPRequestReadsRequestBeforeReturning`). Known limits: in "at least one rule" mode a "must not" rule passes every request that simply leaves that header out, so on its own it lets almost everyone in (the page says so, it is not refused); "remove before forwarding" works only inside the rule's path, so a rule limited to `/admin` leaves the header on every other path; the tick box is also offered for "be absent" rules, where it only matters for requests that are let in although they carry the header (an excepted address, or another rule passed in "at least one" mode); the status code box accepts 500 to 502 while typing, the server refuses them on save; the exception check looks at each address family alone and does not stop a list that leaves out only a few addresses; with "at least one rule", rules limited to another path do not count, a path no rule covers is not checked, and when nothing passes the action of the first applicable rule is used; "remove before forwarding" applies to every request that is let in and is inside the rule's path, also for excepted addresses and for rules that did not pass in "at least one" mode, and it removes every value of that header; the exception list is compared with the client address the site's access rule sees, so forwarded-for headers count only when that access rule trusts proxy headers (otherwise it is the TCP peer, which behind a CDN is the CDN); at most 200 exceptions per site; own status codes send no extra headers (no `WWW-Authenticate` for 401, no `Retry-After` for 429 or 503); the mode and the exceptions belong to the site, not to a single rule; Security > Rules "migrate" does not propose rules for a site in "at least one" mode and cannot express the header removal.

## Security scan before the rebrand (17 confirmed findings fixed)

Scanned with govulncheck, gosec, a secrets sweep and manual review of the web UI, the API and the deploy files. 38 candidates, 17 confirmed after an independent refutation pass, all fixed with tests. Changes that you can notice:

* **State changes over GET are refused.** The form helpers (`PostPara`, `PostBool`, `PostInt`, `PostDuration`) ignore GET, HEAD, OPTIONS and TRACE, so a link or image can no longer change settings and the CSRF token cannot be skipped. Scripts that used `GET ...?param=` must use POST. No setting restores the old behaviour.
* **Viewer accounts** can no longer download certificate archives (private keys), read the OAuth2 client secret, or start outbound probes (upstream test, HTTP test, TLS inspect, port scan, ping, traceroute, DNS, whois).
* **Secrets in API output:** `/api/proxy/detail` no longer returns basic-auth password hashes, `GET /api/sso/OAuth2` returns a mask instead of the client secret.
* **SSO portal** only redirects to hosts of proxy rules that use it, and a session code only works on the host it was issued for. Other redirect targets get HTTP 400.
* **Admin listeners** have header and idle timeouts (10 s header, 120 s idle).
* **First admin setup from another machine** needs the setup token printed in the log.
* **Forward proxy:** public client addresses get 403 by default (admin can allow with `POST /api/tools/fwdproxy/publicclients allow=true`), listener timeouts, optional login.
* **Docker:** the shipped compose file no longer mounts the Docker socket and the image no longer ships sudo and openssh. `docker/docker-compose.socket-proxy.yml` is the opt-in for the container picker.
* **Windows Web SSH** verifies the host key (known_hosts under conf, prompt on first use).
* **Plugin info page** shows plugin-supplied text as text and links only for http, https and mailto. **Port scan tool** accepts only bare IP addresses.
* **Dependencies:** golang.org/x/net to v0.62.0 and related x/ modules (HTTP/2 server advisories).

Known limits: not exercised in a real browser (portscan, plugin info, Web SSH prompt) or against a real Docker daemon; the gorilla/csrf origin-check advisory (GO-2025-3607) is kept as a follow-up, see the scan notes. ## Dunree rebrand

The product is now **Dunree** ("Reverse proxy and web gateway"), published by Foley IT under AGPL-3.0. It is based on Zoraxy v3.3.6 by tobychui and imuslab; the Dunree version line starts at v1.0.0-beta.1. Plan and decisions: `docs/rebrand/plan.md`. Rules: `tools/rebrand/policy.json`.

### Mechanical rename (`tools/rebrand/rename.py`)

One scripted pass renamed everything that is compile-time or display-only. It does not change what an existing install sends, stores or accepts.

* **Go module path:** `github.com/foleyit/dunree` in `src/go.mod`, every import, the tool modules and `tools/nt6.1_go_mod`. The path is a placeholder and is read from one variable, `MODULE_ROOT` in `tools/rebrand/policy.json`. To change it: edit the variable, run `python3 tools/rebrand/rename.py --apply`, build. <!-- rebrand:keep -->
* **Plugin SDK package:** the Go package and its folder are now `dunree_plugin` (`src/mod/plugins/dunree_plugin`, and the vendored copy `mod/dunree_plugin` in every example plugin). The example modules are `example.com/dunree/<name>`. The identifiers that had the name in them follow (`DunreePort`, `DunreeVersion`, `DunreeUUID`, ...). The JSON field names on the wire are unchanged. <!-- rebrand:keep -->
* **Text:** the name in the admin interface, the translation files (keys and values in all locales, because the keys are the English text), messages, e-mail and notification subjects, docs, README, build and CI files.
* **Files:** `docs/nginx2dunree.html`, `docs/plugins/gen_dunree_plugin_doc.sh`, "What is Dunree Plugin" and "dunree_plugin API" in the plugin docs.
* **Plugin verdict rule:** a plugin may set neither `X-Zoraxy-*` nor `X-Dunree-*` headers; both prefixes are reserved. <!-- rebrand:keep -->

What the pass leaves alone on purpose is listed, with the reason and the plan row, in `tools/rebrand/legacy-allow.txt`: the `X-Zoraxy-*` headers, `/.zoraxy/` paths, `zoraxy_*` cookies, metric names, plugin payload fields, browser storage keys, `ZORAXY_*` environment variables, User-Agent values, release asset and backup names, the binary, unit and install path names, plugin IDs, the admin session cookie name, upstream's URLs, and the key-derivation labels that must never change. `python3 tools/rebrand/rename.py --left` prints every remaining old name grouped by the reason it stays. <!-- rebrand:keep -->

Tests: `python3 tools/rebrand/test_rename.py` (protected files and strings stay, second run changes nothing, module root comes from the policy, locale keys and values move together, frozen fixtures untouched). `go build ./...`, `go vet ./...` and `go test -p 1 ./...` pass in `src`; every example plugin builds.

Known limits of the mechanical pass:

* **The Dunree names for wire and data surfaces do not exist yet.** After this pass the product says Dunree but still sends and reads only the old names listed above. Adding `X-Dunree-*`, `/.dunree/`, `dunree_*` metrics and the "Also send legacy names" setting is the work of the later packages in the plan; until then nothing changes for an existing install. <!-- rebrand:keep -->
* **A plugin author who imports the SDK from this source tree has to change the import path and the package name** (`zoraxy_plugin` to `dunree_plugin`) and the renamed identifiers. Plugins that are already built keep working: the contract (`api_version` 1), the headers and the payload fields are the same. A copy of the SDK under the old package name is not shipped yet. <!-- rebrand:keep -->
* **Some values that other systems can see changed with the text**, because the plan classes them as plain renames: the WebDAV Basic-auth realm ("Dunree WebDAV", a browser asks for the saved password once more), the sender name and the `[Dunree]` subject prefix of e-mails and notifications (mail filters on the old prefix stop matching), the organisation fields of newly generated self-signed certificates, the default "Dunree Auth" portal name and TOTP issuer for new enrolments, and the description of the systemd scopes of plugins. Existing certificates, enrolments and saved branding are not touched.
* **Version, session cookie and update source are unchanged.** `SYSTEM_NAME` and `SYSTEM_VERSION` still hold the old values (the first is also the admin cookie name, the second drives config migrations), so the About page and `-version` still show 3.3.6 under the old name until the constants are split. **Update:** the About page and the footer show the Dunree version from `mod/brand`; `SYSTEM_NAME`, `SYSTEM_VERSION` and `-version` are as described here.
* **Lowercase names in prose and scripts are mostly not renamed** (`./zoraxy`, `/opt/zoraxy`, `zoraxy.service`, Docker image and compose names). They describe existing installs and are renamed with the packaging work, not blindly. <!-- rebrand:keep -->

The README section on community-maintained parts now says these are parts of Zoraxy and asks not to tag those people in Dunree issues. **Update:** the CAPTCHA footer, its placeholders and the login footer were changed together with their links, see "Brand in the product and the documents" below; `TestCustomFooter` now holds the Dunree default. <!-- rebrand:keep -->

### Upgrade and migration of existing installs

An install made by Zoraxy (upstream 3.3.x or a `v3.3.6-fork.N` build) keeps working when its program file is replaced by Dunree. Nothing is converted. The page for administrators is `docs/migrating-from-zoraxy.md`. <!-- rebrand:keep -->

* **First Dunree start (`mod/legacycompat/firststart.go`, called from `main()` through `runDunreeFirstStart`).** Before anything writes to the configuration folder: when `conf/dunree_install.json` is missing and the install existed before (the same test as the enterprise baseline: a database, a schema stamp or any file in `conf/`), the folder is copied to `<conf>.pre-dunree-<UTC time>` (without `geodb/`, mode 0700) and the database to `<dbpath>.pre-dunree-<UTC time>`. Then the marker is written and three NOTICE lines go to the log. Later starts see the marker and do nothing. A new install only gets the marker. The step never changes, moves or deletes an existing file. A copy that fails is removed, logged as a warning and tried again at the next start; the start goes on.
* **Cookies of the admin interface.** New names `dunree_session` (constant `ADMIN_SESSION_COOKIE`, no longer `SYSTEM_NAME`) and `dunree_csrf`. The old names `Zoraxy` and `zoraxy_csrf` are accepted, so nobody is logged out and a page that was open during the upgrade can still save. Because the cookie name is part of the signature, the old cookie is verified under its old name and the same content is signed again under the new one (`mod/auth/legacy_session.go`, `mod/legacycompat/csrfcookie.go`, wiring in `dunreecompat.go`). The session keeps its expiry, its account checks and its revocation by password change; logout removes the old cookie too. <!-- rebrand:keep -->
* **Environment variables.** `legacycompat.Getenv("NAME")` reads `DUNREE_NAME`, then `ZORAXY_NAME`, and logs one DEPRECATED line per variable and process when the old one is used (never the value). `METRICS_TOKEN` uses it. <!-- rebrand:keep -->
* **Browser storage.** The admin UI stores under `dunree_...` / `dunree....`. `script/safestorage.js` copies every `zoraxy_...` / `zoraxy....` key to its new name once per browser (marker `dunree.storage.migrated`), never overwrites a value that already exists under the new name and leaves the old keys in place. `zxStore.migrated` reports what the copy did. The UI smoke scripts and docs use the new key names. <!-- rebrand:keep -->
* **systemd.** `tools/install/migrate-from-zoraxy.sh` (run by the owner as root; `--dry-run` first) stops `zoraxy.service`, moves `/opt/zoraxy` to `/opt/dunree` with a link at the old path, writes `dunree.service` from the old unit (folder path replaced, `Conflicts=zoraxy.service` added, drop-ins copied), disables the old unit **without deleting it**, then enables and starts the new one if the old one was enabled and running. A failing step is undone and the old service started again. A second run reports "Already migrated". The program never renames a unit or a folder by itself. <!-- rebrand:keep -->
* **Docker.** Documented only: keep the volumes and the mount paths, change the `image:` line.

Off by default / unchanged: no setting was added. Fresh installs see no difference except the marker file. Existing installs get the one-time copy and the new cookie names; everything they stored keeps being read.

Tests: `mod/legacycompat` (first start on a realistic folder with a real database and API token: every file byte-identical afterwards, copy complete, idempotent, new install, lost marker, failed copy retried, large and folder databases, linked folder; environment precedence and the single log line; CSRF cookie with the real gorilla/csrf middleware including forged cookies; the service script against a temporary root with a fake systemd folder and a fake `systemctl`: full run, dry run, undo on failure, kept service state, refusals, service only), `mod/auth/legacy_session_test.go` (old cookie accepted and re-issued, expiry kept, forged / other key / revoked refused, session without expiry not re-issued, logout, inert without legacy names), `src/dunreecompat_test.go` (pinned names; old browser against the admin handler chain of `main()`; first-start glue), `src/storagekeys_test.go` (no UI file uses an old key; with `PY` set it runs `tools/ui-smoke/storage_migration_smoke.py` in Chromium), and the same check inside `tools/ui-smoke/run.sh`.

Known limits:

* **Cookie names use an underscore** (`dunree_session`, `dunree_csrf`), like the other `dunree_*` cookies of the plan, and the session cookie is `dunree_session`, not `Dunree` as plan row 5 said: a cookie name should not follow the product's display name a second time.
* **Going back to the previous program logs administrators out once**, because the old session cookie was replaced. Configuration and database are still readable by it.
* **Sessions without a server side expiry** (issued by builds from before that existed) are accepted under the old name on every request but not re-issued, so their 30 day limit is not restarted. Such a browser keeps the old cookie until the next login.
* **A CSRF token adopted from the old cookie gets a fresh 12 hours once.** The old CSRF cookie is not removed; it runs out by itself within 12 hours.
* **The first-start copy needs disk space** (about `conf/` without `geodb/`, plus the database). A database over 1 GiB is not copied; the marker and the log say so. There is no free-space check beforehand: a copy that runs out of space is removed and tried again at every start until it fits.
* **The copy goes next to the configuration folder, by its absolute path.** With `-conf .` it is `<working folder>.pre-dunree-...` in the parent folder (it used to be placed inside the folder it copies and copy itself until the path was too long). A database inside `conf/` is copied twice (with the folder, without the 1 GiB limit, and on its own). On Windows a symbolic link inside `conf/` needs the right to create links; without it the copy fails and is tried again at every start.
* **The marker is exported with the configuration** (`confpack` does not list `dunree_install.json` as per install), so importing a full export from another install replaces this install's marker with that install's (its origin, time and copy paths are then wrong; nothing is copied or lost, as the import can only happen after the first start here). Not changed here because `confpack` belongs to another area.
* **The marker is a file in `conf/`.** A full configuration import replaces it; the next start writes it again and takes no second copy while the first one exists. If the first copy was deleted, a new one is taken. The copies are never pruned automatically.
* **The copy and the notice are only in the log**, not in the admin interface.
* **Browser storage is copied once.** A choice changed later with the previous program is not copied again. The login page (which does not load the helper) reads the language under the old key until an admin page has made the copy. Keys of plugin pages are not touched.
* **The data-tab id `zoraxy_sso_tab`** on the SSO page looks like a storage key but is not one; it was left alone. <!-- rebrand:keep -->
* **The service script** handles one unit file in one folder (default `/etc/systemd/system`), plain paths and the default or given install folder. It refuses a mount point, an existing target folder and a target on another file system (a move there would be a copy and a delete that cannot be undone half way). In the unit it replaces the folder path only where it is the whole path: a longer path that only ends the same (`/usr/local/opt/zoraxy`) is left alone. <!-- rebrand:keep -->
   It does not rename the program file, does not edit cron jobs, log rotation or backup scripts (the link at the old path keeps them working) and was tested with a fake `systemctl`, not on a live systemd. It is a script, not a `dunree migrate-service` subcommand.
* **Environment variables of the release and plugin-index signing tools** (`ZORAXY_RELEASE_KEY`, `ZORAXY_RELEASE_PUB`, `ZORAXY_PLUGIN_INDEX_KEY`) are not changed by this work; they belong to the release tooling. <!-- rebrand:keep -->
* **Docker is documentation only.** The image, its paths and its label still carry the old names in `docker/`; the image name for Dunree is not decided, and the page says so. **Update:** `docker/` uses the Dunree names now, see "Final leftover audit" and "Dunree rebrand: finish".
* **The marker records the version constant of the build** (`SYSTEM_VERSION`, still the base version until the constants are split).

### Wire protocol and plugin compatibility

Names that other programs see now have a Dunree form. The form Zoraxy used keeps working. One switch decides whether the old form is still *sent*; the old form is always *accepted*. Code: `src/mod/wirecompat`, `src/wirecompatapi.go`, `src/mod/plugins/wire.go`. <!-- rebrand:keep -->

**The setting.** Listeners > Compatibility > "Also send legacy X-Zoraxy-* headers". On by default, also on an install that was upgraded (no stored value means on). It applies immediately, is stored in the database (`settings` / `legacyEmit`) and is logged at start while it is on. API: `GET /api/compat/legacy`, `POST /api/compat/legacy` with `enable=true|false` (a GET never changes it; viewer accounts cannot change it). The card also lists which old paths were requested since the start. <!-- rebrand:keep -->

|---|---|---|---|---|
| Response headers to visitors | `X-Dunree-Ref`, `X-Dunree-Captcha-Reason`, `X-Dunree-Error-Page` | `X-Zoraxy-Ref`, `-Captcha-Reason`, `-Error-Page` | while the setting is on | not read |
| Webhook request headers | `X-Dunree-Event`, `X-Dunree-Timestamp`, `X-Dunree-Signature` | `X-Zoraxy-Event`, `-Timestamp`, `-Signature` | while the setting is on, same values (the header name is not part of the signed text) | not read |

**Plugins.** A plugin built with the Zoraxy SDK (`zoraxy_plugin` 1.0.0 to 1.2.0), or written for Zoraxy without an SDK, is found, started and called as before, without being rebuilt. Its configure payload is key for key what Zoraxy sent. The plugin channel does not follow the setting above on purpose: without the old header such a plugin cannot verify its invoke token and refuses every call, and a fail-open filter would then let traffic pass without a message. New plugins use the Dunree SDK, `dunree_plugin` 2.0.0 (`src/mod/plugins/dunree_plugin`): it declares `sdk_flavor: "dunree"`, reads the Dunree names and falls back to the Zoraxy names, so the same binary also runs on a Zoraxy-fork host of contract version 1. The contract version is still 1. Both kinds are written down in `docs/plugins/contract.md`, section 10, with the steps to move a plugin to the new SDK. <!-- rebrand:keep -->

Known limits:

* **The setting covers three things only:** response headers to visitors, webhook headers and metric names. It does not cover the plugin channel, the cluster headers or anything that comes in. Its label names the headers; the help text names the metrics. <!-- rebrand:keep -->
* **Metrics double in size while the setting is on.** Every series is exported as `dunree_*` and as `zoraxy_*`, so a scrape is about twice as large and a Prometheus that stores both stores twice the series. Turn the setting off when dashboards and alert rules use `dunree_*`. Recording rules that sum over `{__name__=~".+_http_requests_total"}` count twice. There is no separate switch for metrics only. <!-- rebrand:keep -->
* **The value of the metrics realm changed** (`dunree-metrics`). Nothing is known to compare it. The `version` label of `dunree_build_info` is still what `SYSTEM_VERSION` says. <!-- rebrand:keep -->
* **Old paths are answered, not redirected**, and stay for the whole 1.x line. A custom CAPTCHA page that has `/.zoraxy/captcha/verify` written out keeps working; one that uses `{{.VerifyPath}}` now posts to `/.dunree/captcha/verify`. <!-- rebrand:keep -->
* **Mixed versions behind one load balancer.** A challenge page made by a Dunree node posts to `/.dunree/captcha/verify`. If the answer lands on a node that still runs a Zoraxy build, that node does not know the path and passes the request to the upstream. Upgrade all nodes that serve the same site before relying on CAPTCHA, or pin visitors to a node during the upgrade. The same holds for a monitor that is switched to `/.dunree/health` before every node is upgraded. <!-- rebrand:keep -->
* **A site whose own application uses a path under `/.dunree/`** loses exactly the three paths above to the proxy, as it already did under `/.zoraxy/`. <!-- rebrand:keep -->
* **The once-a-day log of old paths is per process**, starts again after a restart, and the counters shown on the Compatibility card are not stored. <!-- rebrand:keep -->
* **The setting is per node.** It is not part of the cluster or fleet settings sync and not in the configuration history; set it on each node. <!-- rebrand:keep -->
* **Plugins always get both header names and the `zoraxy_*` fields in 1.x.** There is no way to turn that off. A plugin sees up to seven more header lines per call. A plugin built for Zoraxy sees `zoraxy_version = 3.3.6` and cannot see the Dunree version. <!-- rebrand:keep -->
* **A plugin without the SDK that wants `dunree_port`** has to declare `"sdk_flavor": "dunree"` in its manifest; `zoraxy_port` is always there and is the same port. <!-- rebrand:keep -->
* **A Dunree SDK plugin on a Zoraxy host**: that host does not overwrite `X-Dunree-*`, so a client of the proxy can send them. Where the host sets the `X-Zoraxy-` twin (capture, URI, request ID) the two values differ and `HostHeader` takes the `X-Zoraxy-` one (a Dunree 1.x host always sends the pair with the same value; review fix, tested in `TestDunreeSDKReadsHostHeadersUnderBothNames`). A host header that a Zoraxy host does not set at all for a call can still be supplied by a client. The invoke token is not affected. On a Dunree host both names are overwritten. Not tested against a real upstream Zoraxy binary, only against its wire format. <!-- rebrand:keep -->
* **The old SDK package is no longer shipped** under `src/mod/plugins/zoraxy_plugin` (the plan had it as a thin deprecated copy). The last one is kept as a frozen test fixture (`testdata/sdk-1.2.0`); authors keep building with the copy in their own plugin. <!-- rebrand:keep -->
* **Not renamed here:** the IDs of the reference plugins (`fork.zoraxy.ref.*`: stored plugin settings belong to the ID), the `zoraxy.csrf.Token` meta tag and `{{.csrfToken}}` placeholder of plugin pages, the plugin store address and index format, cookies, User-Agent values, hook environment variables, mDNS names and `X-Auth-Method`. The help text under the webhook secret in the certificate tools and the plugin author pages under `docs/plugins/docs` still name only the `X-Zoraxy-*` headers (true while the setting is on; plugins always get them). `DEVELOPMENT.md` still lists the `zoraxy_*` metric names and `/.zoraxy/` paths. <!-- rebrand:keep -->
* **UI:** the new card was not looked at in a browser by a person; the toggle text is English and is translated when the locale files get the two new strings. <!-- rebrand:keep -->

### Add-on store

The App Store no longer has a store built in. Dunree ships **without a store source** and contacts no store until an administrator adds one. Format and behaviour: `docs/plugins/addon-store.md`. Publishing: `docs/plugins/publishing-addons.md`.

* **No default call to upstream.** The address of the plugin store of the Zoraxy project is gone from `start.go`; `ManagerOptions.PluginStoreURLs` is empty in the Dunree binary. With no source, the start-up sync and the Refresh button fetch nothing (log line "No add-on store configured"). The links to the upstream plugin documentation and issue tracker were removed from the App Store page. <!-- rebrand:keep -->
* **Existing installs keep their source (not silent).** An installation that existed before its first Dunree start (the probe the enterprise baseline uses: a database, a schema stamp or files in the config folder) gets the store it always synced from written into its source list **once**. It is shown as "Zoraxy community store (third party)", the log says so at that start, and it can be removed like any other source; once removed it does not come back. A new installation never gets it. The address is one constant, `LegacyZoraxyStoreIndexURL` in `src/mod/plugins/store_sources.go`; set it to `""` to migrate nothing. <!-- rebrand:keep -->
* **Empty state with three choices.** System > App Store shows "No add-on store configured" and offers **Dunree add-on store** (one click), **Custom index URL** and **Local folder**. The Sources dialog offers the same three and labels every source by kind. Installed apps whose source is no longer configured are named in a notice ("get no updates") with a button to add the source again.
* **The Dunree add-on store address is one constant, to be set by the owner:** `DunreeAddonStoreIndexURL` (with `DunreeAddonStorePublicKey`) in `src/mod/plugins/store_sources.go`. It is a placeholder today (`.example` host). While it is a placeholder the one-click choice is shown as "not open yet", is disabled, the API refuses it in words, and nothing is contacted.
* **Local folder source.** A folder on the server with an `index.json` (and `index.json.sig`) and the program files. No network, works in offline mode. Files are only read from inside the folder of a configured local source; an index on the web can never point Dunree at a file of the server.
* **Dunree add-on index, format version 1** (`"format": "dunree-addon-index"`): id, name, publisher, version, `api_version`, `min_host_version`, licence, categories, permissions, changelog, screenshots, icon, and per-platform artifacts (`linux_amd64`, `windows_amd64`, `darwin_arm64`, ...) each with URL, SHA-256 and size. Signed with the existing plugin index key (detached ed25519 signature at `index.json.sig`, serial number against replay) and checked with the existing modes off / warn / enforce. Install, update, health check and rollback are the existing ones. Artifact addresses may be relative to the index. The older signed plugin index and the list format are read as before.
* **Platform selection.** Only the artifact whose key is exactly this server's `GOOS_GOARCH` is installed; the program is stored with `.exe` on Windows. An add-on without a build for the server is listed with a note and cannot be installed.
* **Minimum host version.** An add-on that needs a newer Dunree is listed with "Needs a newer Dunree" and its install is refused by the server in every verification mode (new format only).
* **`tools/addon-store`** (standalone Go program, standard library only): reads one folder per add-on with an `addon.json`, verifies the program files (inside the folder, `.exe` only for Windows, ELF / PE / Mach-O header and CPU type match the platform key, optional checksum and `-introspect` comparison), and writes `index.json`, `index.json.sig`, `index.pub`, a browsable `index.html` and the versioned program files. Signing is done by `tools/plugin-index/sign_plugin_index.go`, which got the mode `-sign-raw` (signs a finished add-on index without changing a byte; `-verify` reads the format too). The generator never opens the private key.
* **API:** new read-only `GET /api/plugins/store/setup`; `POST /api/plugins/store/sources/add` also takes `kind=dunree` and `kind=local&folder=...` (`url=...` works as before); sources carry `kind`, `label`, `folder`, `schema`; entries of an add-on index carry `Addon`.

Tests: `src/mod/upstreamguard` (scans shipped Go and web sources for hosts of the upstream project; only comments, credits and a short list with reasons pass; the Dunree store address appears in one place), `src/mod/plugins/addonindex` (parsing, validation, platform selection, `.exe`, versions), `src/mod/plugins/store_addon_test.go` (no source and no connection by default, the migration runs once and is removable, signature states and installs per mode, replay, platform choice, minimum host version, a web index cannot name local files, local folder end to end with the real generator in offline mode including update, rollback and a tampered file), `tools/addon-store/main_test.go`, `tools/plugin-index/sign_plugin_index_test.go`, and the App Store part of `tools/ui-smoke/smoke.py` (`--netsys-only`). The two older tests in `store_test.go` that fetched the real upstream index now use a local test server.

Known limits:

* **The Dunree add-on store does not exist yet.** Address and public key are placeholders for the owner to set; until then only custom URLs and local folders work.
* **Upgraded installations still contact the Zoraxy community store** at start and on Refresh until an administrator removes that source. This follows `docs/rebrand/plan.md` row 26 (existing installs: migrated as-is). The one upstream address left in the product is that migrated value. <!-- rebrand:keep -->
* **"Existing installation" is decided conservatively.** A config folder that holds any file counts as existing, so a new installation whose folder was prepared by hand (or by a deployment tool) before the first start also gets the migrated source. It is visible and removable.
* **One public key for all sources**, no per-source keys and no key rotation inside the format.
* **One version per add-on in an index.** No channels, no install of an older version from the store (rollback uses the copy Dunree kept).
* **Exact platform match only:** no fallback between architectures, no `GOARM` / `GOAMD64` level, no musl / glibc distinction.
* **Local folder:** read on the server Dunree runs on (in Docker it must be mounted); its icons and screenshots are not shown, because the browser cannot load files of the server.
* **The minimum host version is compared only when the host version reads as `major.minor.patch`**; otherwise the add-on installs with a note. The comparison uses the version plugins are told (`SYSTEM_VERSION`).
* **An icon that cannot be downloaded fails the install**, as before, for every index format.
* **Featured card:** apps are featured when an add-on index marks them `featured`; for the migrated community store the previous rule (apps of its maintainers) is kept.
* **Wording:** the page and navigation entry are still called "App Store"; the new texts are English until the locale files are regenerated (`tools/i18n/extract.py`). **Update:** the page and the navigation entry are called "Add-ons" and the locale files are regenerated, see "Dunree rebrand: finish".
* **The upstream-host test has an allow list** for links a person clicks and identifiers that belong to other parts of the rebrand (footer credit links, the CAPTCHA footer default, the default page of the static web server, mDNS identity strings). Those are not calls Dunree makes; they are listed with reasons in `src/mod/upstreamguard/guard_test.go` and should shrink as those parts are finished.
* **Not looked at by a person in a browser** beyond the screenshots of the smoke run (light theme, 1366 px and 390 px).

Review fixes (adversarial review of the store):

* **A file of the server is read only for an entry of the local source whose folder holds it.** Before, any index (a web index in the list format, or a second local source) could name a `file://` address inside the folder of *some* configured local source and have it installed. `stageDownload` now refuses an artifact address of a file unless the entry came from a local source and the file is inside that source's own folder (`localArtifactRefused`, test `TestLocalArtifactOnlyFromItsOwnSourceFolder`).
* **The path that is checked is the path that is opened.** `copyLocalArtifact` checked `dir/link/../x` lexically (as `dir/x`) but opened it through the link. It now cleans the path before both (same test).
* **The upstream-host test no longer lets credit wording excuse a load.** A web line with `src=`, `fetch(`, `$.get`, `<link`, `url(`, `<iframe` and similar never counts as attribution, whatever words it carries ("upstream" is everyday wording in a reverse proxy) (`TestCreditWordingDoesNotExcuseALoad`).
* `pluginStoreExistingInstall` has a test of its own (`src/pluginstore_glue_test.go`).

Known limits of these fixes: a symbolic link *inside* a local source folder that points elsewhere is still followed when the file is opened (the administrator chose the folder, and under enforce the checksum of the signed index must match); a hard cut of the migrated Zoraxy community store is still the owner's decision (`LegacyZoraxyStoreIndexURL`). <!-- rebrand:keep -->

### Deployable on every platform (Windows service, packages, release matrix, CI)

Dunree now builds for Windows, macOS, Linux and FreeBSD from one source tree, can run as a Windows service, and has install files for each system in `packaging/` (overview: `packaging/README.md`). Nothing here changes what an existing Linux install does: the new code only runs when the first argument is the word `service` or when Windows starts the program as a service.

**Builds.** `go build ./...` and `go vet ./...` pass for linux, windows, darwin and freebsd (amd64), and `go build ./...` for windows/arm64, darwin/arm64, linux/arm64, arm, 386, riscv64 and mipsle. One thing had to be fixed: `src/mod/sshprox` chose its embedded files with a list of platforms, so windows/arm64 (and every platform not on the list) did not compile. The fallback file `embed.go` is now the exact complement of the per-platform files, and `embed_windows.go` covers Windows on CPUs other than amd64. The signal, restart, process-group and disk code already had per-system files and needed no change.

**Windows service** (`src/service.go`, `service_windows.go`, `service_other.go`; uses `golang.org/x/sys/windows/svc`, which was already in `go.mod` as an indirect dependency and is now a direct one):

* `dunree.exe service install [--dir FOLDER] [--manual] [-- -flag=value ...]`, `service uninstall | start | stop | status`. `status` exits 0 running, 3 stopped, 4 not installed.
* As a service Dunree works in `%ProgramData%\Dunree` (or `--dir`), so the usual relative defaults (`./conf`, `./sys.db`, `./log`, `./plugins`) are below it. The folder is created so that only SYSTEM and Administrators can read it; an existing folder keeps its permissions. The folder is stored with the service as the new flag `-service_dir`, which has no effect anywhere else.
* Console output and crash traces go to `<data folder>\log\service.log` (moved to `service.log.1` at a start when larger than 10 MB); start, stop and failures also go to the Application event log.
* The service reports "starting" until the admin port is bound. Stop and the pre-shutdown notice of Windows run the normal stop sequence (`shutdown.go`, drain included) and the service reports "stopped" afterwards, so a clean stop is not counted as a failure. A crash or a failed start is restarted by Windows after 5 s, 15 s, then every minute.
* Flags given after `--` are checked at install time: an unknown flag, a flag without `=value`, and flags that make the program exit at once (`-version`, `-doctor`, ...) are refused, instead of producing a service that fails at every start.
* Changes in `main.go` are three lines: the entry check, the stop channel (so the service manager can ask for the same stop as SIGTERM) and the exit hook.
* Inside the Windows service no SIGINT / SIGTERM handler is registered (`notifyStopSignals`). Windows sends every service `CTRL_LOGOFF_EVENT` whenever any user logs off, and the Go runtime turns that into SIGTERM once a handler exists: the service would have stopped cleanly, and therefore without a restart, at every RDP or console logoff. The service is stopped through the service manager only. Test: `TestStopSignalsNotRegisteredInsideService`. A console start on any system subscribes to both signals as before.

**Packaging** (`packaging/`): Windows (zip layout, `install.ps1` / `uninstall.ps1`, Inno Setup script `dunree.iss`, winget manifest templates and `render.sh`), macOS (launchd job, `build-pkg.sh`, package scripts), Linux (`dunree.service` for the tarball, `install.sh`, nfpm configuration for `.deb` and `.rpm` with their own unit, `/etc/default/dunree` and maintainer scripts), FreeBSD (rc.d script), containers (multi-architecture `Dockerfile` that cross-compiles the program, `compose.yaml`, `compose.socket-proxy.yaml`). No signing key or certificate is in the tree. Defaults were chosen so that nothing surprising happens: the `.deb` / `.rpm` and `install.sh` do not enable or start the service, firewall rules are only added on request, `compose.yaml` publishes the admin port on 127.0.0.1 only and does not mount the Docker socket, and no file contains a registry, download or project address (they are variables or arguments).

**Container compatibility.** The new image keeps the environment variables of `docker/entrypoint.py`, the ports, the old container label and, through a link from `/opt/zoraxy` to `/opt/dunree`, the old volume paths. ZeroTier is still built in by default (`WITH_ZEROTIER=false` leaves it out).

**Release script** (`tools/build_release.sh`): builds `dunree_<os>_<arch>[.exe]` for linux (amd64, arm64, arm, 386, riscv64, mipsle), windows (amd64, arm64) and darwin (amd64, arm64); `--targets` builds a subset (and is the only way to get freebsd/amd64 and freebsd/arm64), `--dry-run` prints the plan without building or needing a key, `--packages` adds the archives and packages before signing. Signing and the verify step are unchanged. Because the updater of an existing install asks for `zoraxy_linux_<arch>`, every Linux binary is also written under that name as a byte-identical copy in the same signed `SHA256SUMS` (`--no-legacy-names` leaves them out). `tools/sign_release.go` signs `dunree_*` and `zoraxy_*` files and reads `DUNREE_RELEASE_KEY` before `ZORAXY_RELEASE_KEY`; the script also looks in `~/.dunree-release-key/` before `~/.zoraxy-release-key/`. The header line of `SHA256SUMS` is unchanged. The module path used for the build-time addresses (`DUNREE_SOURCE_URL` and others) is read from `src/go.mod`, not written in the script.

**CI** (`.github/workflows/ci.yaml`, `docker.yml`): every action is pinned to a commit with its version, the workflows have `contents: read` only, and there are new jobs: a build matrix of twelve targets (with `go vet` once per operating system), the Windows service end to end on a Windows runner (install, start, answer, clean stop, uninstall, plus `install.ps1` and the Inno Setup compile), a macOS job (start, clean stop, plist, package build), and a packaging job (the checks below, `.deb` / `.rpm` with a pinned nfpm, a container build). The image workflow builds `packaging/container/Dockerfile`, takes the image name from the repository variable `DOCKER_IMAGE` and is skipped while that is not set; the upstream image namespace is no longer a default.

Tests: `src/service_test.go` (command line of `service`, every real flag accepted or refused as intended, data folder and stored arguments round trip, log rotation, the stub off Windows, a normal start is not affected and the stop still ends through the exit hook); `tools/sign_release_test.go` (Dunree and legacy names signed together, other files left out, tampering caught, key variable precedence); `tools/build_release_test.sh` (argument handling and `--dry-run`; with `--build` a real build of linux/amd64 and windows/amd64 with a throwaway key: packages, signature, legacy copy identical, the binary starts, answers and exits 0 on SIGTERM, a wrong key aborts); `packaging/test.sh` (shell syntax, both units with `systemd-analyze verify`, plist, every YAML file, action pinning and permissions of the workflows, structure of the PowerShell and Inno Setup files, archive layout and reproducibility, `.deb` contents, `install.sh` dry run and refusals, winget rendering, no upstream address or namespace anywhere in `packaging/`).

Known limits:

* **Nothing was run on Windows, macOS or FreeBSD.** This work was done on a Linux machine without those systems, PowerShell, Inno Setup or Docker. The Windows service code is compiled and vetted for windows/amd64 and windows/arm64 but has never been executed; the PowerShell scripts and `dunree.iss` were reviewed by hand and checked for structure only; the plist was parsed, `build-pkg.sh` only ran with `--dry-run`; the rc.d script only passed `sh -n`; the `Dockerfile` was never built and the compose files were only parsed. The CI jobs that would run all of this exist but have never run (nothing was pushed). Treat the first green run of `windows-service`, `macos` and `packaging` as the real test, and expect small fixes.
* **Checked here:** the cross builds and vet above, the Go tests, both shell test scripts, and `.deb` / `.rpm` built with nfpm 2.41.1 (the `.deb` was inspected with `dpkg-deb`; neither package was installed, which needs root; the `.rpm` was not inspected with rpm tools). `install.sh` ran in dry-run and refusal cases only. `shellcheck` was not available.
* **A full cross build is large.** Each target adds about 1.3 GB to the Go build cache, about 14 GB for the whole matrix. On the release machine set `GOCACHE` to a folder that is removed afterwards, or have that much free space.
* **`build_release.sh` still compares the tag with `SYSTEM_VERSION`** (3.3.6), because the installed updater does. A `v1.0.0-beta.1` tag is refused until the version constants are split and the updater side of the version reset is done; the header line of `SHA256SUMS` and the updater's asset name are not changed by this work either. `src/Makefile` still writes `dist/zoraxy_*`.
* **The legacy copies** add six files, the size of the six Linux binaries, to every release.
* **Windows service:** it runs as LocalSystem (there is no option for another account), and plugins run as that account. To change the flags or the data folder, uninstall and install the service again (the data folder is kept). A stop requested while Dunree is still starting waits until the stop handler is ready; after 40 s the service is reported stopped and the process ends. A start that fails (for example a port in use that makes Dunree exit) is restarted by Windows again and again; the reason is in `service.log`. The Fleet / cluster restart ends the process and relies on that restart, which Windows records as a failure. `service.log` is only rotated at a start. The Update page cannot update Dunree on Windows or macOS; run the installer or `install.ps1` again.
* **The logoff fix was not seen on Windows:** it is checked with a test of the subscription only; whether a service with no Go console handler survives a logoff relies on the Windows default handler, which the first `windows-service` run does not exercise (no user logs off there). `install.sh --dir` on an existing folder leaves its mode as it is (before this review it made any existing folder, `/opt` for example, mode 0750); a new folder is still created 0750 (`packaging/test.sh` checks the dry run).
* **`dunree service ...` off Windows** prints where the unit files are and exits with 2. Before, the word was ignored and the program started; a start command that happens to pass `service` as a first argument must drop it.
* **Web SSH** on platforms without an embedded terminal helper (darwin/arm64, FreeBSD, linux/riscv64, linux/mipsle) is as unavailable as it already was on riscv64 and mipsle; Windows on arm64 uses the same pure-Go terminal as Windows on amd64.
* **Packages:** not code-signed or notarised (SmartScreen and Gatekeeper warn); the steps for the owner are in `packaging/README.md`. With the `.deb` / `.rpm` the program is upgraded by the package manager and the Update page cannot replace it. The arm package is labelled `armhf` and holds the ARMv6 hard-float build. The macOS package version drops a pre-release suffix (`1.0.0-beta.1` becomes `1.0.0` inside the package; the file name keeps it). The winget manifests need the installers built on Windows and addresses that do not exist yet.
* **Container:** the old `docker/` folder (Dockerfile and compose files of the previous image) is left as it is; the workflow no longer uses it. Inside the new image the entry script still starts the program through the old name (a link), so the process list shows that name.
* **FreeBSD and macOS builds are provided as they are:** compiled and vetted for every change, with no test run on those systems outside the new CI job for macOS.

**Updater.** Dunree compares its own version with Dunree releases only.

* Release tags are Semantic Versioning tags, `v<major>.<minor>.<patch>[-<pre-release>]`, ordered by that precedence alone: `v1.0.0-beta.1` < `v1.0.0-beta.2` < `v1.0.0-beta.10` < `v1.0.0-rc.1` < `v1.0.0` < `v1.0.1`. The time a release was published no longer takes part.
* A release of the source counts only when it carries program files named `dunree_<os>_<arch>` (`.exe` for Windows). It is installed only when the signed first line of `SHA256SUMS` is `# dunree-release product=dunree tag=<tag> build=<n> upstream=<base version>`. The signature is checked with the same ed25519 release key as before; no key was created or changed.
* The releases of the fork Dunree comes from (v3.x tags, other file names, the header `# zoraxy-release`) are skipped in the list, whatever their version number, and because they are signed with the same key they are also refused by name at the header. With only such releases in the source the Update page says "The update source ... has no Dunree release on the ... channel" instead of an error or an offer. <!-- rebrand:keep -->
* A tag with a pre-release part is offered on the beta channel only, also when the pre-release box of the release was not ticked.
* Before a downloaded program is installed it must print exactly the version of the tag for `-version` (`1.0.0-beta.2` does not pass for `1.0.0`, nor the reverse).
* `conf/updater/installed.json` now records the product. A record without it (written by the updater of the fork) is not trusted, so its build number cannot block a Dunree release.
* The update source is still the policy variable `UPDATE_REPO` (`-update_repo` overrides it); it was not changed.

**Release tooling.** `tools/build_release.sh` requires the tag to be `v` plus `PRODUCT_VERSION` and refuses any other (a tag of the base version, a tag in the fork's form, a tag without the pre-release part). It writes `dunree_*` files only; the copies under the earlier file names are no longer made (`--no-legacy-names` is still accepted and does nothing). New test mode `--targets-subset LIST`: builds the named targets like `--targets`, and marks the folder with `NOT-A-COMPLETE-RELEASE.txt` so that a quick trial of the whole path is not mistaken for a release. The full release is unchanged: six Linux targets, two Windows, two macOS. `tools/sign_release.go` writes and requires the new header, takes `-upstream`, refuses to sign a folder that holds a file under the earlier name, and reads `DUNREE_RELEASE_KEY` / `DUNREE_RELEASE_PUB` before `ZORAXY_RELEASE_KEY` / `ZORAXY_RELEASE_PUB` (the key folder fallback `~/.zoraxy-release-key/` is unchanged). `src/Makefile` writes `dist/dunree_*` and has `make version`. <!-- rebrand:keep -->

Off by default / unchanged for existing installs: `conf/version`, the configuration files, backups and what earlier plugins are told are byte for byte what they were. What an upgraded install does see change is listed under the known limits.

The older notes above ("Two version numbers are still in the program", "`build_release.sh` still compares the tag with `SYSTEM_VERSION`", "The legacy copies add six files") describe the state before this work.

**Review fixes (version, updater, release tooling).**

* A numeric pre-release identifier with a leading zero (`v1.0.0-beta.01`) is no longer a release tag, as Semantic Versioning says. It had the same precedence as `v1.0.0-beta.1`, so two releases under different tags could not be ordered. The updater (`ParseTag`), the sign tool and `tools/build_release.sh` refuse it alike. No such version is planned.

### Origin check of the admin interface (gorilla/csrf v1.7.3, GO-2025-3607)

**What was wrong.** gorilla/csrf v1.7.2 never compared where a request came from: its Referer check could not run, and it had no Origin check. A request that changed something was accepted on cookie and token alone, so a page on another origin that knew a matching pair (another port or a sibling name of the same site, or a page injected over plain HTTP) could save settings in the name of a logged-in administrator. This was the follow-up left open by the security scan.

**What changed.** The library is v1.7.3, which checks the `Origin` header, or the `Referer` when there is none, on every request that is not GET, HEAD, OPTIONS or TRACE. Taken as it is, v1.7.3 assumes HTTPS and refuses every save on a plain HTTP admin interface, so the new package `src/mod/csrfguard` tells it per request how the browser reached the admin interface (`src/admincsrf.go`, used by `newAdminCSRF` in `src/dunreecompat.go`):

| How the admin interface is reached | What is done | Needs a setting |
|---|---|---|
| directly, plain HTTP (`-webui_tls off`, the default) | the request is marked with `csrf.PlaintextHTTPRequest`; an `Origin` must be `http://` + the `Host` header | no |
| directly, HTTPS (`-webui_tls auto` / `custom`) | nothing is marked: `Origin` must be `https://` + `Host`; without `Origin` the `Referer` must be an https page of the same host | no |
| through a proxy that ends TLS and passes the `Host` header on (a Dunree rule, Caddy, Traefik, nginx with `proxy_set_header Host $host`) | the browser says `https`, so an https origin is compared with `Host`; with `X-Forwarded-Proto: https` an http page is refused | no |
| through a proxy that replaces `Host` but sends `X-Forwarded-Host` (a Dunree rule with a host override, Apache `ProxyPass`) | an `Origin` that is exactly the first `X-Forwarded-Host` value counts as the own address | no |
| through a proxy that replaces `Host` and sends no `X-Forwarded-Host` (nginx `proxy_pass` without `proxy_set_header`) | refused until the address is listed | `-csrf_trusted_origins` |
| a script: cookie and token, no `Origin`, no `Referer`, no `Sec-Fetch-Site` | accepted as before, over HTTP and HTTPS | no |

"The same host" ignores case and the default port of the page's scheme in `Host` and `X-Forwarded-Host` (`admin.example.com:443` for an https page, `:80` for an http page), because some proxies write it (nginx `proxy_set_header Host $host:$server_port`) while a browser never does; v1.7.3 alone compares exactly and refused those saves. The scheme is still compared, so `Host: admin.example.com:443` with an http page is refused. Found in the independent review; test `TestSameHostWrittenDifferently`.

Two new command line switches, both off by default:

* `-csrf_trusted_origins` (empty): comma separated extra addresses, `host`, `host:port` or `https://host[:port]`, as the browser shows them. No wildcards. A list that cannot be read stops the start with a message instead of being ignored.
* `-csrf_strict` (off): `X-Forwarded-Host` is not used, and over HTTPS every client, also a script, must send an `Origin` or a `Referer`.

A refused request gets `403` with the library's line (`Forbidden - origin invalid`, `referer invalid`, `referer not supplied`) and a second line that names the address it came from, the address it arrived for and the switch with the value to set; an http page of an https admin interface is named as that instead. The same goes to the log under `[csrf]`, at most once per address and minute. The two switches are logged at start when one is set.

The library's own `csrf.TrustedOrigins` option is deliberately not used. It compares the host only, so it accepts an http page of a listed host for an https admin interface. That is a second advisory, GO-2025-3884, for which no fixed version exists. A listed address is handed to the library as the own address instead, so the scheme is compared too.

**Other dependencies (govulncheck over the whole module).** Before: three advisories in code that is called (GO-2025-3607 gorilla/csrf, GO-2026-6974 go.opentelemetry.io/otel, GO-2026-6278 gorilla/websocket). `go.opentelemetry.io/otel`, `otel/metric` and `otel/trace` went from v1.44.0 to v1.47.0 (this adds the indirect module `otel/log` and moves `go-logr/logr` to v1.4.4), and `golang.org/x/crypto` from v0.58.0 to v0.59.0 (with it `x/sys` v0.50.0, `x/text` v0.44.0, `x/sync` v0.25.0), which removes the module-level note about `x/crypto/openpgp` (not imported). After: one advisory in called code, see the limits.

Unchanged for existing installs: cookie names, cookie attributes, the token and where pages put it, the REST API (`/api/v1`, bearer token) and the plugin API (`/plugin/`), which are outside this check. An admin interface opened directly, from a script or through a Dunree rule works without a setting. What can change is the fifth row of the table; `docs/migrating-from-zoraxy.md` ("Admin interface behind another reverse proxy") and `DEVELOPMENT.md` ("Where a change may come from") describe it. <!-- rebrand:keep -->

Tests: `src/mod/csrfguard/csrfguard_test.go` (the real library on real plain and TLS listeners, table tests: browser, script, other site, opaque origin, broken Origin, downgrade, the two requests of the advisory, hidden Origin and Referer, missing and wrong token in every accepted case, PUT/DELETE/GET; proxy that keeps the Host; proxy that replaces it with and without `X-Forwarded-Host`, chains, another port; `X-Forwarded-Proto`; listed origins with and without scheme, look-alike and sub-domain names, both listener kinds, strict on and off; the refusal text and one log line per address; the handler behind the check receives the request unchanged; the list parser with thirteen refused forms), `src/admincsrf_test.go` (go.mod is at v1.7.3 or later and go.sum no longer lists v1.7.2; both switches default to off; `newAdminCSRF` as `main()` uses it on real listeners with the defaults and with each switch), `src/dunreecompat_test.go` and `src/mod/legacycompat/csrfcookie_test.go` (the cookie of an upgraded install still works with the new library), `tools/e2e-admin/scenarios/s14_csrf_origin.py` against started instances (`tools/e2e-admin/run.sh --only csrf-origin`): the token flow with curl over plain HTTP, over `-webui_tls auto`, and through a Dunree rule that points at the instance's own admin port with the Host passed on and replaced; `-csrf_strict`, `-csrf_trusted_origins` and a list with a wildcard; and Chromium: fetch and form from the admin page over HTTP, HTTPS and through the rule, and the same form with the matching token on another port of the same host (the browser sends the cookie) is refused and logged. Three tests that put `csrf.Protect` in front of a plain HTTP handler themselves now mark their requests as plain HTTP (`posture_api_test.go`, `secdashboard_test.go`, `mod/legacycompat/csrfcookie_test.go`).

Known limits:

* **Existing installs, one case changes without a setting:** an admin interface behind a proxy that replaces the `Host` header and sends no `X-Forwarded-Host`. Pages load, every save answers 403 until the program is started with `-csrf_trusted_origins=<address in the browser>` or the proxy passes the `Host` header on. The login page shows only its general error ("Something went wrong...") for that 403; the reason is in the answer of the request and in the log. The admin pages were not changed to show it.
* **The same for a proxy that says `X-Forwarded-Proto: https` while the browser uses plain http:** saves are refused with the "http page" message. Open the admin interface with https, or correct the header.
* **A client that sends none of `Origin`, `Referer` and `Sec-Fetch-Site` is taken for a script** and needs only cookie and token, as before this change. Every current browser sends `Origin` with a POST; a very old browser, or one whose extension removes all three headers, gets no origin check over HTTPS unless `-csrf_strict` is set. `-csrf_strict` breaks scripts that send no `Referer` over HTTPS (curl, the e2e client), which is why it is off.
* **Plain HTTP without TLS anywhere:** without an `Origin` header the `Referer` is not looked at (the library has no such rule for plain HTTP), and on a plain listener without `X-Forwarded-Proto` an http and an https page of the same host both count, because the program cannot know which one the browser used. Somebody who can change plain HTTP traffic can do more than that anyway; use `-webui_tls` or a TLS proxy that sends `X-Forwarded-Proto`.
* **Without `Origin`, only the `Host` header counts for the `Referer`.** A listed address or an `X-Forwarded-Host` address is accepted through `Origin` only.
* **Only the default port of the page's own scheme is ignored.** A proxy that writes another port into `Host` (for example the port of its own listener behind a port forward, `Host: admin.example.com:8443` for a page at `https://admin.example.com`) is another address; list it with `-csrf_trusted_origins` or pass the browser's `Host` on. A path in the refusal log line is quoted, so a line break in it cannot start a fake log line.
* **`X-Forwarded-Host` and `X-Forwarded-Proto` are believed from whoever connects to the admin port.** A page of another site cannot make a browser send them (the admin interface answers no CORS preflight), and a script that has cookie and token needs no help. `-csrf_strict` ignores `X-Forwarded-Host`; `X-Forwarded-Proto: https` can only make the check stricter.
* **The switches are command line only.** There is no setting in the admin interface and a change needs a restart (for an install started from a script: the line in that script).
* **Still reported by govulncheck:** GO-2026-6278 in gorilla/websocket v1.5.3 (weak random source for the mask key of outgoing WebSocket frames; called from the WebSocket proxy) is fixed only in an untagged commit that also reworks the client, proxy and server code of that library. It was not taken. GO-2025-3884 is listed for the imported gorilla/csrf package, with no fixed version; the affected option is not called.
* **Not tried against real nginx, Apache, Caddy or Traefik.** Their rows in the table follow from the headers they send by default; only a Dunree rule in front of the admin port was run, plus the same headers sent by curl and in Go tests. Chromium was the only browser.
* **The full browser smoke (`tools/ui-smoke/run.sh`) passed on the build with v1.7.3 and the per-request marking, before the listed origins and `X-Forwarded-Proto` were finished.** Neither takes part when the admin interface is opened directly; the Chromium scenario above ran on the final build. The live part of the plugin smoke (`plugins_run.sh`) and the e2e scenario `plugins-filter-example-lifecycle-hooks-ui` fail at this checkout in the plugin manager itself ("plugin not found" / "plugin is already running" as the answer of the handler, so behind the check). A save from a plugin page inside the admin interface was therefore not seen in a browser with this change; such a page is framed with `allow-same-origin`, so its requests carry the admin origin.
* **WebSocket connections of the admin interface** (GET requests) are not part of this check, as before.
* **`docs/verification/e2e-admin.*` was not regenerated;** the five new scenarios are not in it yet.

### Swap script for the two proxies (`tools/install/swap-to-dunree.sh`)

The two proxies do not have the `/opt` layout that `tools/install/migrate-from-zoraxy.sh` handles: a root unit starts `/home/sysadmin/start.sh`, which runs the program file in the same folder with its flags. `swap-to-dunree.sh` is for exactly that layout. The owner runs it with sudo, on Proxy1 first, then on Proxy2. The page with the commands is `docs/deploy/swapping-from-zoraxy.md`.

* **Before anything changes:** root; the new program file (SHA-256 against `--sha256`; against `SHA256SUMS` next to it, whose first line must be the header of a Dunree release; the raw ed25519 signature `SHA256SUMS.sig` with the release key of the updater, a copy of which is in the script, or with `--pubkey`; `-version` must answer as Dunree); free disk space; the old unit active, the admin port in `ss`, the admin page answering `curl -k`. An unsigned or unchecked file is a `WARN` with the hash, never silent. A wrong hash, a signature that does not fit and a `SHA256SUMS` of another product refuse the run.
* **What it records to compare afterwards:** the TCP ports the old main process listens on plus the ports named by flags in `start.sh`, the plugin programs running from `plugins/`, the number of files in `conf/proxy`, and the first enabled host rule in `conf/proxy` that answers through the proxy on 127.0.0.1 (ports 443 and 80 first). Nothing of this is hard-coded.
* **Backup** in `backups/pre-dunree-<UTC time>/` (0700): `program.tgz`, the old unit, `plugins.list`, `README.txt` with the restore commands, and `data.tgz` (`conf`, `sys.db`, `sys.uuid`, `plugins`) taken after the stop so the database is closed.
* **The swap:** stop the old unit; install `<dir>/dunree` (755, root), the old program file stays; rewrite only the program path in `start.sh` (copy `start.sh.pre-dunree`, flags compared before and after, owner and mode kept); write `dunree.service` from the old unit (`Description`, `SyslogIdentifier=dunree`, `Conflicts=<old unit>`, everything else as it was, drop-ins copied); disable the old unit and keep its file; `daemon-reload`, `enable` (only when the old unit was enabled), `start`.
* **Checks for up to 60 s (`--timeout`)**, then once more five seconds later with the same main process: unit active, admin port, admin page, `conf/dunree_install.json`, the same plugin programs, the same ports, the same number of rule files, the proxied host.
* **A failed check, the time-out, an error or a signal:** stop and disable the new unit, end processes of the new program that are left, put `start.sh` back, move `dunree.service` into the backup folder, enable and start the old unit, check it (active, port, admin page), remove the program file this run installed. Exit 1, or 3 when the old service is not healthy at the end. The data is left as it is, except that `data.tgz` is restored (what was there is moved aside, not deleted) when the number of rule files changed or when the old service does not come up on the data.
* **`--rollback`** does the same by hand and leaves `<dir>/dunree` in place; `--restore-data` also restores `data.tgz`. **`--dry-run`** runs the checks and prints the `start.sh` and the unit it would write. **`--no-start`** stops after `enable`. **`--role dev|live`** is required: `live` refuses when the old service is not healthy or less than 1 GB is free, and asks for the host name before the first change; on `dev` an unhealthy old service is a warning.
* **Second run:** "already swapped", nothing changed, exit 0 (1 when the new unit is not active). A half-finished state (only one of unit, `start.sh`, `start.sh.pre-dunree`) is refused with the advice to run `--rollback`, which cleans it up.
* No network access: the script talks to 127.0.0.1 only. One lock file per folder (`backups/.swap-to-dunree.lock`); the lock is not passed on to the service.

Unchanged for existing installs: nothing runs by itself. The program never calls the script.

Tests: `tools/install/test_swap.sh` (40 tests since the review below, about two minutes, no root). Each test builds the layout in a temporary folder with stand-in program files, `tools/install/testdata/systemctl-shim.sh` (really starts and stops what `ExecStart` names) and stand-ins for `ss`, `curl` and the process list: dry run changes no file; the full swap (unit content, flags including `-fleet_port :8010`, backup content, order of stop and start, every output line prefixed); second run; roll back by hand and swap again; `--restore-data`; one test per failing check (program exits, no marker, admin page, a plugin missing, a port missing, proxied host, program dies while it is checked, a rule file lost with data restore); old program that cannot read the new data (data restore); roll back that fails (exit 3); SIGTERM during the checks; `live` confirmation and refusals; `dev` with a stopped old service; low disk space; checksum, `SHA256SUMS`, signature good, wrong key, changed file, short signature, header of another product; the key in the script equals `src/mod/updater/release_pubkey.pem`; other layouts refused; half-swapped state; `--no-start`; a unit that was not enabled and drop-ins; `-port` written with a space, an address and quotes; `bash -n`, shellcheck when installed, no outside address in the script.

Shown: a full swap (all checks, 13 s down), an automatic roll back with real programs (a "new" program that writes no marker; program file, `start.sh` and unit byte-identical afterwards), the second run, `--rollback` (the old program started on the data Dunree had used), a `live` swap with a signed `SHA256SUMS`. On the Dunree side: copy and marker made, the copy of `conf` and of the database identical to the state at the stop, 63 rule files loaded, a real host answered 200 through the proxy port, the three third-party plugins built against the old SDK (Data-Shield Blocklist 1.3.0, Resource Monitor 1.0.3, the Cloudflare WAF plugin 0.3.4) found, started and `running` with health `ok` in `/api/plugins/status`. Known limits:

Dunree on the real database, the cluster between the two proxies with one of them swapped, CrowdSec and SSO are only seen in the real run.
* **Never run against real systemd.** Stop of the control group, `Conflicts=`, `enable`, the journal, root, ports 80 and 443 and plugin processes in systemd scopes are covered by the shim's imitation at most. The first real run is the one on Proxy1.
* **Only this layout.** A unit whose `ExecStart` is not `<dir>/start.sh`, a `start.sh` without the full path of the old program file, or flags that move `conf`, the database, `sys.uuid` or `plugins` are refused. One program line in `start.sh` is assumed; flags are read from the first one.
* **Plugins are compared as running processes, not through the plugin API** (the script has no admin password). A plugin that runs but is unhealthy inside passes. A plugin that did not run before the swap is not expected afterwards. The rehearsal asked the API by hand.
* **Rules are compared by the number of files in `conf/proxy`**, not by what the proxy loaded. One host is asked through the proxy; a rule that breaks only for other hosts is not seen. If no enabled rule answers on 127.0.0.1 before the swap, that check is skipped with a warning.
* **A port from the range for outgoing connections** that the old program listened on (it has one helper port on 127.0.0.1) is only a warning when it is missing afterwards, because it is a different number at every start.
* **The data is not restored by a normal roll back.** The old program reads what Dunree wrote (rehearsed on an empty database only). Administrators have to log in again after going back. The marker and Dunree's own copies stay.
* **Downtime** is the stop, the `data.tgz` of the stopped data, the start and Dunree's own first-start copy: 13 to 14 s in the rehearsal with a small database, not measured with the real 95 MB one. A failed swap adds the time of the checks (up to `--timeout`) and the restart of the old service.
* **The signature check needs OpenSSL 3.** Without it, or without `SHA256SUMS.sig`, the script warns and goes on (the `live` prompt shows "NOT VERIFIED"). The release tag and build number in the header are shown, not compared with anything. A build of the owner's own has no signature at all: `--sha256` is then the only check, and it only proves the file is the one whose hash was typed.
* **`-version` of the new file is run as root** before it is installed, in an empty temporary folder, but never when its checksum or signature was found wrong. A file that is not executable gets `u+x` in the staging folder. A file that came without `--sha256` and without `SHA256SUMS` is run unverified (with a `WARN`).
* **`start.sh` on the proxies belongs to a normal user and is run as root.** The script warns and does not change the owner.
* **Other things that name the old unit** (cron jobs, monitoring, scripts) are not searched or changed. The journal identifier changes to `dunree`.
* **Nothing is ever cleaned up:** the old program file, the old unit, `start.sh.pre-dunree`, the backup folders and Dunree's copies stay until the owner removes them (the page lists the commands). Two swaps in the same second would use the same backup folder name; the second is refused.
* **`test_swap.sh` is not wired into CI or `go test`;** run it by hand. It uses stand-ins, so it proves the script's logic, not the product.
* **Seen in the rehearsal, not caused by the swap:** the Data-Shield Blocklist plugin logs `initial blocklist load failed: unexpected HTTP status 404` under both programs, and the journal of the running Proxy1 has it too.

#### Review of the swap script (2026-11-25)

An independent review read every line, ran the tests and injected failures. Fixed:

* **A dropped ssh session left the proxy half swapped.** SIGHUP and a terminal (or pipe) that is gone made the next write end the script with SIGPIPE (status 141) before the roll back, so `start.sh` and `dunree.service` stayed and the old unit stayed stopped. Now SIGPIPE is ignored from the first change on, a failed write to the terminal is ignored, and every line also goes to `backups/pre-dunree-<time>/swap.log` (the lines of the checks before it are written there first). SIGHUP rolls back like Ctrl+C.
* **A second Ctrl+C, a `kill` or SIGHUP during the roll back could end it half way** (the handler reset the signals to their defaults). The roll back now ignores INT, TERM, HUP and PIPE and runs with `set +e` to the end. `--rollback` by hand ignores HUP and PIPE (Ctrl+C still stops it) and writes `rollback-<time>.log` into the latest backup folder.
* **`--rollback --restore-data` after a roll back moved the data away under the running old program** and, as root, would have killed its plugin processes as "left over". `go_back` now stops the old unit first when it is active and starts it again at the end.
* **A file with a wrong SHA-256 or signature was still run as root (`-version`).** It is now never run.
* **A full disk while `data.tgz` was written left the half file** (and so a full disk) for the old service that was started again. Half-written `data.tgz`, `program.tgz` (when the backup step itself fails), `<dir>/dunree.swap-new` and `dunree.service.swap-new` are removed.
* **Flags were read up to the last mention of the program path on the line,** so `exec <dir>/zoraxy -port=:3000 >><dir>/zoraxy.log 2>&1` gave the flags `.log 2>&1` and the default admin port 8000: on `dev` the swap then failed its checks and the roll back ended with exit 3. Now the first mention counts.   <!-- rebrand:keep -->
* **A failing `systemctl enable` or `daemon-reload` rolled back with only "unexpected error"**; they now have their own `FAIL` line. An `Alias=` of the old unit is left out of the new one (it would make `enable` fail).
* **`<dir>/dunree` being a folder or a link** was found only after the stop; it is now refused before anything changes, and the program file and the unit are put in place with `mv -T`.
* **A dry run without root ended with `FAIL: unbound variable`** (and as root any failing command inside a `$(...)` could have put its `FAIL` line into the captured value): with `set -E` the error trap also ran in command substitutions and printed into them. It now reports only from the main shell, and the disk sizes always come out as a number (`du` fails for a folder it cannot fully read). After the fix a read-only `--dry-run` as the normal user against the real Proxy1 layout (with a stand-in program file) passed every check it can make without root: layout, flags `-port=:3000 -webui_tls auto`, admin page 307, 63 rule files, one real host 200.
* The stand-in `systemctl` starts programs with default signal handling (`env --default-signal`), as systemd does, so the test of the roll back is not slowed by ignored signals.

New tests (11): a `du` that fails inside the disk check; SIGHUP with the reader of the output gone (old state back, `swap.log` has the result); Ctrl+C, TERM and HUP sent again and again during the roll back; `--rollback --restore-data` after a roll back (old unit stopped, data restored, started again); a file with a wrong `--sha256` is never run; `tar` failing with "No space left" while writing `data.tgz` (roll back, no half file); `systemctl start` failing; `systemctl enable` failing; a `start.sh` with comments, `ulimit`, `export`, `cd` and a log redirection naming `<dir>/zoraxy.log` (only the program path changes, flags and admin port right); an `Alias=` in the old unit; `<dir>/dunree` being a folder.   <!-- rebrand:keep -->

Known limits after the review:

* **`kill -9` of the script, a power cut or a reboot mid-way are not handled.** After the stop and before `start.sh` is rewritten, such a state is not seen as half swapped: the old unit is just stopped. On `live` the next run refuses because the old service is not running; start it (`systemctl start zoraxy`) and run again. Later states are seen as half swapped and `--rollback` cleans them up.   <!-- rebrand:keep -->
* **After a dropped session the swap rolls back** rather than going on. The owner reads the result in `swap.log` in the backup folder, or runs the swap inside `tmux`/`screen` to avoid it.
* **shellcheck was not run** in the review (not installed on Proxy1, and a downloaded copy was not allowed to run); quoting was checked by hand. The unquoted expansions left are lists of process or port numbers and the paths in the README text, which are checked to be plain before.
* With SIGPIPE ignored, the commands the script runs get a write error instead of SIGPIPE when a reader goes away early. The pipelines in the script read small outputs (the listening ports, one line of `start.sh`); this was checked, not tested with large outputs.

### Screenshots

**`docs/img/screenshots/` holds pictures of Dunree.** 22 PNG files with a caption each: the first-start page and the login page, Status (light, dark and at phone width), the HTTP Proxy list, the site editor with its upstreams and load balancing, certificates, Security Overview, Security Center, WAF, Rules, CrowdSec, Statistics (top of the page and the visitors part), Uptime Monitor, Add-ons (without a source and with a local signed index), Fleet, Cluster / HA, the error page designer and About Dunree with the attribution. The top-level README shows 17 of them in its "Screenshots" section, `docs/img/screenshots/README.md` shows all of them, and the documentation index (`docs/README.md`, `docs/index.html`) lists that page. The ten pictures of the old website that were in this folder (`1.png` to `10.png`) are gone; the other pictures left in `docs/img` (`logo.png`, `logo_white.png`, `icon.png`, `brand/`) already show the Dunree mark and were kept.

**How they are made.** `tools/screenshots/run.sh` builds Dunree from the checkout and starts `tools/screenshots/capture.py`. That starts four throw-away instances in a temp folder (the one that is photographed, which is also a Fleet hub, and three nodes that join it), eleven small upstream web servers on loopback addresses, the fake CrowdSec Local API of the UI smoke harness and a local add-on index built and signed with `tools/addon-store` and a key that is made for the run. It creates the administrator through the first-start page, seeds sites under `example.com` and `example.test`, certificates made with openssl, rules, WAF, auto-ban, bot rules, error pages and a Fleet roll-out through the admin API, and sends demo requests through the proxy port while it works. The pictures are 1440 x 900 at twice the pixel density (the phone picture 390 x 844), reduced to an 8 bit palette, between 40 and 340 KB each, 3.0 MB together. `capture.py --docs-only` rewrites the README section and the gallery page from the list of pictures in the script, without a browser. A run removes pictures that are no longer in the list.

Unchanged for existing installs: nothing in the program changed. The tool never reads a real configuration: every instance runs in a new temp folder with `-offline`, its admin port on 127.0.0.1.

Tests: `python3 tools/screenshots/test_screenshots.py` (18 tests, standard library only: the folder holds exactly the pictures of the list, each one is a PNG with an 8 bit palette, the expected pixel size, under 450 KB and without text or time chunks; the old pictures stay away; `manifest.json`, the README section and the gallery are what the script writes, and writing them twice changes nothing else in the README; every picture a text shows exists and every picture is shown; the documentation index lists the gallery; host names in the demo data are example names, upstreams are loopback addresses, visitor addresses are documentation ranges or public resolvers and never a private range; the PNG writer round trip). `python3 tools/docs/test_docs.py` covers the index page. Every picture in the repository was looked at after the run; pictures that showed an unfinished page were taken again (the first run showed an empty Statistics page and a top bar without its status pills on two pictures, which is why the script now waits for the words listed in `MUST` and for the top bar).

Known limits:

* **The test cannot see what a picture shows.** It checks files and texts. Whether a page is complete, in the right theme and free of messages is checked by the script only in part (it waits for words every picture must show, and refuses a page that shows a toast, an empty or loading state, the name of the machine, one of its addresses or the home folder of the user) and otherwise by looking at each picture after a run.
* **The host name is replaced in the pictures.** Dunree shows the host name of its machine under Status > System resources and uses it for a Fleet node. The script rewrites that one word in the answers of the admin API to `dunree-demo` before the page gets them. Nothing else is changed in an answer. CPU, memory, disk and the network throughput charts of the Status page are the real values of the machine the run was made on.
* **Visitor addresses.** Most demo requests carry addresses of the documentation ranges, which Dunree counts as "Local network". For the country lists the rest carry addresses of public DNS resolvers (9.9.9.9, 1.1.1.1 and so on, the list is `VISITORS` in the script); they are visible in "Top client IPs" of `statistics-visitors.png`. No address of a private network is used.
* **Upstreams are shown as `127.0.10.x:port`.** They are servers on loopback addresses of the machine; on a system without the whole 127.0.0.0/8 range, or when a port is taken, the script falls back to `127.0.0.1` and a free port, and the pictures show that.
* **Live data.** Numbers, times, charts and the reference in the error page preview differ from run to run, so a new run changes every file. The traffic runs for 12 minutes by default (`MINUTES`); the pictures in the repository were made with 30, because the Status chart covers 30 minutes and the uptime monitor checks every 5 (`sites.png` and `site-editor.png` were taken again in a second run of 12 minutes, so their "blocked today" number is lower than on the other pictures). "Yesterday", "7 days" and "30 days" of the Statistics page would be empty and are not shown.
* **Multi-upstream sites say "Not checked" in the Live column of the HTTP Proxy list** (`sites.png`: www, api and app.example.com), although the Uptime Monitor checks each of their upstreams. That is how the page behaves today, the picture was not retouched. It is a gap of the list, not of the screenshots.
* **The add-ons of the local index are examples.** Their program files are placeholders (`-skip-binary-check`); nothing is installed from the index. Add-ons of a local folder have no pictures of their own, so the cards show the default icon.
* **The login page has one look.** It does not follow the theme, so there is no dark variant of `setup.png` and `login.png`.
* **A fixture stands in for a backup.** The script puts an empty `dunree-pre-update-*.zip` into the backup folder of the throw-away instance so that "Make a backup" is not open on the Status page. One site is down and one certificate is close to expiry on purpose, so the top bar shows both warnings.
* **Colours are reduced to 256 per picture** (median cut, no dithering). Flat areas keep their exact colour; the gradient of the login page shows faint bands at full size.
* **Needs** a Python with Playwright and Chromium, openssl, Go and Linux; about 600 MB of memory for the four instances. Chromium was the only browser. The script was run on one machine.
* **Not in the pictures:** the pages that are not in the list (Visitors, Access Rules, SSO, CAPTCHA, Stream Proxy, Redirection, Plugin Manager, Update, Settings and the network pages), other languages than English, and the node side of Fleet.
